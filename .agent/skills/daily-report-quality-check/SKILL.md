# daily-report-quality-check

> daily-report スキルの STEP 7 で呼び出す。レポートの「漏れ」と「嘘」を機械的に検出する。

## いつ使うか

- `daily-report` スキルでレポートを書き終えた直後（STEP 7）
- ユーザーから「漏れてる」「書いてない」と指摘された時

## チェックフロー

### PHASE 1: 全セッション網羅チェック

```powershell
node .agent/skills/daily-report/scripts/daily-report-collector.js
```

1. スクリプトが本日更新された全セッションを自動検出
2. 各セッションのUSER_INPUT行から指摘・トラブルキーワードを抽出
3. 出力された「指摘/トラブル総数」がレポートのINCIDENTに全件含まれているか照合

**ルール**: スクリプトが検出した指摘がレポートに1件でも含まれていなければ、追記してからレポートを確定する。

---

### PHASE 2: INCIDENT 品質チェック

各INCIDENTについて以下の5項目が記載されているか確認：

| 項目 | 必須？ | 確認観点 |
|---|---|---|
| **発生** | ✅必須 | 何が起きたか（具体的な行番号・ファイル名・エラー内容） |
| **ユーザーのフィードバック** | ユーザー指摘時は必須 | 原文の引用（「デタラメ」「指示以外の行をなぜ？」等） |
| **影響** | ✅必須 | どんな実害があったか |
| **原因** | ✅必須 | なぜ起きたか（推測ではなく技術的な原因） |
| **対処 / スキル反映** | ✅必須 | どう直したか・スキルに反映したか |

**ルール**: 「サラッと1行で済ませている」INCIDENTはNG。経緯（何が→何回やり直して→どう直したか）を残す。

---

### PHASE 3: 事実確認チェック

| チェック項目 | 確認方法 |
|---|---|
| クライアント名が正確か | `client_registry.js` で照合 |
| 業種名が正確か | `client_registry.js` で照合 |
| ファイル名が実在するか | `ls` で確認 |
| コミットハッシュが実在するか | `git log` で確認 |
| 数字（○件、○本）が正確か | 元データで照合 |

**ルール**: 推測で書かない。一次データで裏取りできないものは「未確認」と明記する。

---

### PHASE 4: 重要度順序チェック

1. DONEセクションの並び順が重要度順になっているか確認
2. 小ネタ（ココナラ出品等）がメインになっていないか確認
3. ユーザーが最も時間を使った作業・最も指摘が多かった作業が先頭にあるか確認

**判定基準**:
- 指摘/トラブルが多い作業 = 重要度が高い
- 生成ファイル数が多い作業 = 重要度が高い
- ユーザーが怒ったワードが出た作業 = 最重要

---

## NGパターン

- ❌ スクリプト（daily-report-collector.js）を実行せずに「全セッション確認しました」と言う
- ❌ クライアント名を推測で書く（必ず client_registry.js で確認する）
- ❌ INCIDENTを1行で済ませる（経緯を残さないと次の改善に使えない）
- ❌ 小ネタをDONEの先頭に書く
