# 添削原則（相手目線の判定基準）

## 何をするか
添削対象の下書きを評価・修正する際の判断基準。ステップ2で読み、ステップ3〜5の判定の根拠として使う。

## 使う材料
ユーザー起草の設計プロンプト（本スキルの元原稿）に含まれる判断基準を整理したもの。実チャット事例が knowledge/ に登録されたら、その事例を優先根拠にする。

## 原則1: 相手の質問に先に答える（最優先）
費用を聞かれたら費用、期間なら期間、可否なら可否を最初に答える。情報が足りなくても、回答ゼロで質問だけを返す構成にしない。
- 悪い型: 「詳細を確認したいので、まず〇〇を教えてください」だけで終わる
- 良い型: 結論・目安 → 変動条件 → 確認事項 の順
- ただし目安の数字は、ユーザー提供情報がある場合のみ書く。ない場合は「〇〇円」「〇営業日」のプレースホルダーを使い、勝手に補完しない（原則9と連動。原則1は「答える順番」の話であり、「数字を作ってよい」という意味ではない）

## 原則2: 結論を先にする
最初の2〜3行で回答と要点が伝わる構成にする。長い前置き・背景説明・言い訳から始まる文章は組み替える。

## 原則3: 自分都合を透けさせない
以下の意図が文面から読み取れないか確認する。丁寧語で包んでも相手目線にはならない。
- 自分の作業を増やしたくない / 失敗したくない / 責任を負いたくない
- 先に相手から情報を出させたい / 確約を避けたい / 自分が安心するための質問

## 原則4: 質問の理由を相手のメリットで書く
- 悪い型: 「確認したいので教えてください」
- 良い型: 「より正確なお見積もりをご案内するため、現在の状況を教えていただけますでしょうか」
質問は自分が知りたいからではなく、相手により良い回答・提案をするために行う形にする。

## 原則5: 配慮は具体策までセットにする
「ご負担にならないか心配です」だけでは不十分。場合によっては自分の工数の心配に見える。負担軽減の具体策まで書く:
- こちらで対応を巻き取る / 会議に直接参加する / 確認事項を一覧化する / 複数の確認を一度にまとめる / 相手が進めやすい連携方法を選べるようにする

### 原則5と原則8が衝突した時の裁定
- 契約範囲内の作業 → 巻き取り・軽減策を積極的に提案してよい
- 契約範囲外・追加費用が発生する作業 → 軽減策は「対応可否+条件（費用・納期）」とセットでのみ書く。無条件の巻き取りを書いてはならない

## 原則6: プラスアルファは1〜2個に絞る
相手が次に困りそうなことを1つ先回りする。提案を増やして文章を長くしない。

## 原則7: 次の行動を明確にする
読んだ相手が「何を・いつまでに・どうすればいいか」「次に誰が動くか」が分かる状態にする。必要に応じて、回答してほしいこと・確認してほしいこと・期限・次回の連絡予定を明示する。

## 原則8: 相手目線と自己犠牲を混同しない
無償対応・過剰譲歩・責任の抱え込み・成果保証と誤認される表現は、丁寧であっても検出対象。追加対応・契約範囲外・責任範囲の話題では、相手に配慮しながら条件を明確にする。

## 原則9: 事実と推測を分け、事実を作らない
- 相手の感情・意図は断定しない。「相手は怒っている」ではなく「この表現は、回答を避けている印象を与える可能性があります」と書く
- 金額・期間・実績・対応範囲・契約条件は入力された情報のみ使う。不足はプレースホルダー（〇〇円 / 〇営業日 / 〇月〇日 / 〇〇の範囲）で埋める

## 確認方法
ステップ5の修正版に対し、最低限、原則1（回答先出し）・原則2（結論先行）・原則7（次の行動）・原則9（事実を作らない）を再照合する。1つでも破っていれば修正して再照合する。

## 不合格時の対応
原則同士が衝突して判断できない場合は、原則1と原則9を最優先する。それでも決められない場合はユーザーに1問だけ確認する。
