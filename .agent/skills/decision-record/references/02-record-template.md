# 記録ファイルのテンプレートと書き方

## 目的

記録を「検証済みの事実だけを含む、100行以内の不変な文書」として統一するための型。

## 使う材料

- 工程2で収集した検証済み事実（変更ファイルのパス・実行コマンド・検証結果）
- 未検証・未対応として分類した項目
- 採用案・不採用案とその理由

## 保存先と命名

- 保存先: `.agent/history/`（`.agent` はスキル基盤のルートフォルダ。skills/ と同じ階層）
- ファイル名: `YYYY-MM-DD_<内容を表す英語スラッグ>.md`（小文字英数字とハイフンのみ。例: `2026-07-07_gbp-meo-skill-retirement.md`）
- 同日に複数イベントがある場合はスラッグで区別し、1イベント1ファイルを守る

## 記録本文のテンプレート

以下のセクション構成をそのまま使う。全セクション必須（書くことがないセクションは「なし」と明記する）。

```markdown
# YYYY-MM-DD <イベントの表題>

種別: 破壊的変更 / 設計判断 / インシデント（該当するもの）
関連: <関連する過去の記録・スキル・クライアントへのリンク。なければ「なし」>

## 方針（なぜやったか）
<背景と決定内容を3〜10行。採用しなかった案がある場合は案と却下理由も書く>

## 実施事項（何をしたか）
<変更したファイル・フォルダの実パスを列挙。移動は「元→先」の形式で書く>

## 検証結果
<実行したコマンドや確認手順と、その結果。検証していない場合は「検証なし」と正直に書く>

## 未対応・未検証
<やり残し・裏付けのない事項。なければ「なし」>
```

## 見る観点（書き方のルール）

- 事実のみ: 実在を確認したパス・実行した結果だけを書く。「〜のはず」「おそらく」は未対応・未検証欄へ
- 100行以内: 超えそうなら詳細を影響ファイル側（アーカイブのREADME等）に置き、記録からリンクする
- 不変: 作成後は書き換えない。訂正は新規記録を作り相互リンクする
- 自己完結: 記録単体で読めるように、社内略語やセッション内の呼び名を使わず正式名で書く

## 索引（INDEX.md）の行フォーマット

記録ファイル作成後、`.agent/history/INDEX.md` に必ず1行追記する:

```markdown
- [YYYY-MM-DD 表題](ファイル名またはパス) — 種別 / 一言サマリ
```

INDEX.md がなければ、見出し `# 履歴索引` と説明1行を付けて新規作成する。

## 確認方法

- テンプレートの4セクションが全て存在するか
- 実施事項の全パスが実在するか（1つ以上を実際に確認する）
- 100行以内か
- INDEX.md に対応する行が追加されたか

## 不合格時の対応

- セクション欠落 → 追記してから完了報告する
- 100行超過 → 詳細を外部ファイルへ移しリンクに置き換える
- 未検証の断言が混入 → 「未対応・未検証」欄へ移す
