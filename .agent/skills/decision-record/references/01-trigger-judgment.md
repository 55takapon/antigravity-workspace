# 発火判定の基準

## 目的

「全セッション一律の作業ログ」ではなく「後で必ず探すことになる出来事」だけを記録するための判定基準。記録の価値は量に反比例するため、この判定が本スキルの品質の要になる。

## 使う材料

- 今回のセッションでユーザーと交わした依頼・承認の内容
- 実際に変更・削除・移動したファイルの一覧
- 実行したコマンドと検証結果

## 記録対象の3類型（いずれか1つでも該当すれば記録する）

| 類型 | 該当する例 | 見る観点 |
|:-----|:-----------|:---------|
| ① 破壊的・構造的変更 | スキルの廃止・アーカイブ退避 / ファイル・フォルダの大量移動 / 保存先やパスの変更でスクリプトを書き換えた / 命名規則・保管ルールの変更 | 元に戻すのに記録が必要か。他のスキル・スクリプトへ影響が波及したか |
| ② トレードオフを伴う設計判断 | 複数案から理由をつけて1つを採用した / 本来のルールに例外を設けた / 「今回はやらない」と意図的に見送った | 採用しなかった案と理由を、本人以外（未来のAI含む）が知る手段が他にあるか |
| ③ インシデント・失敗 | 誤削除・誤上書きとその復旧 / クライアント成果物への誤った出力 / 手順ミスから再発防止ルールを作った | 同じ失敗を繰り返さないために、何が原因で何を変えたか |

## 除外条件（該当したら記録しない）

| 除外ケース | 理由 |
|:-----------|:-----|
| 投稿文・レポート・リサーチ等の成果物を作っただけのセッション | 成果物自体（posts/、gbp-clients/ 等）が履歴になっている |
| 1ファイルの軽微な修正・誤字直し | 各スキルの references/changelog.md の1行で足りる |
| 調査・相談だけで何も変更していないセッション | 記録すべき「実施事項」が存在しない |
| daily-report で既に十分カバーされる日常運用の出来事 | 重複記録になる |

## 作業手順

1. セッションの作業内容を時系列で振り返る
2. 3類型のどれに該当するかを1つずつ照合する
3. 該当があっても、除外条件に当てはまらないか確認する
4. 迷った場合は「3ヶ月後に誰かが『なぜこうなっている？』と探す場面があるか」で判定する。探す場面が想像できなければ記録しない

## 出力形式

判定結果は次のどちらかで工程1の結論とする:

- 記録対象: 「類型①（破壊的変更）に該当: スキル12本の廃止・移動」のように類型と根拠を1行で示す
- 記録対象外: 「記録対象外: 成果物作成のみのセッションのため（除外条件1）」のように理由を1行でユーザーに報告する

## 確認方法

- 類型・除外条件のどの行に該当するかを具体的に言えること
- 「なんとなく重要そう」だけを根拠にしていないこと

## 判定に不合格（曖昧）な場合の対応

類型にも除外条件にも明確に当てはまらない場合は、ユーザーに「今回の○○は履歴に残しますか？」と1回だけ確認する。確認せずに勝手に記録を量産しない。
