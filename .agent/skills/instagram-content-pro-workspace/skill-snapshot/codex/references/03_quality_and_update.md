# 品質ゲートと更新手順

このファイルは、成果物の最終確認と、スキル改善依頼で必ず読む。

## 品質ゲート

作成した成果物は、必ず全項目を確認する。不合格が1つでもあれば修正してから返す。

| 項目 | 合格条件 |
|---|---|
| 目的一致 | 認知、保存、相談、購入、来店などの目的に対してフォーマットとCTAが一致している |
| 対象明確 | 誰に向けた投稿かが1文で分かる |
| 一次情報 | ユーザーの体験、実績、顧客の声、実データ、確認済み事例のいずれかが入っている |
| 冒頭 | Reelsは3秒以内、カルーセルは1枚目、キャプションは1行目で止まる理由がある |
| 保存理由 | 読者が後で見返す理由がある |
| 共有理由 | 読者が誰かに送りたくなる具体性がある |
| 独自性 | 他者投稿の焼き直しではなく、視点、検証、編集、文脈がある |
| 導線 | 投稿後に取ってほしい行動が1つに絞られている |
| 計測 | 投稿後に見るKPIと確認タイミングが書かれている |
| 安全性 | 誇大表現、断定、無根拠な効果保証、規約違反がない |
| 成果物分離 | アカウント戦略、プロフィール、月間運用、投稿案、分析と、Reels/カルーセル/ストーリーズ/フィードを混ぜて選んでいない |
| 月間運用 | 月間カレンダーは30行以上あり、投稿しない日も制作、分析、素材回収などの予定が入っている |
| プロフィール | bio、ピン留め、ハイライト、リンク導線で同じCTAや同じ意味の案内を重複させていない |
| 根拠信頼性 | 公式情報、ユーザー提供資料、実インサイトを優先し、ツールベンダー記事や海外事例を無条件に一般化していない |

## よくある不合格と修正

| 不合格 | 修正 |
|---|---|
| ただの一般論になっている | ユーザーの体験、数字、失敗、顧客の声を入れる |
| フックが煽りだけ | 悩み、意外性、結論、証拠のいずれかを入れる |
| CTAが多すぎる | 目的に最も近い1つだけ残す |
| リールが説明過多 | 1カット1メッセージに分け、余白を作る |
| カルーセルが文字だらけ | 1枚につき見出し1つ、本文2から4行へ削る |
| 成功事例の真似になっている | 事例から抽出した作業ルールだけを使い、表現と構成を作り直す |
| 月間カレンダーが10行程度で終わる | 30日分に展開し、投稿なしの日も運用予定を入れる |
| 成果物と投稿形式が混ざる | 先に成果物を選び、投稿を作る時だけフォーマットを選ぶ |
| 素材がないのに撮影前提 | 素材レベルA/B/Cを判定し、既存素材やFAQで代替する |
| bioの行が重複する | 1行は対象、1行は価値、1行は証拠/条件、1行はCTAに分ける |

## スキル更新手順

ユーザーがスキル改善を依頼したら、必ず以下を実行する。

1. 改善対象を特定する。
   - SKILL.md: 工程、発火条件、出力順の改善。
   - references/00_initial_intake.md: 初回ヒアリング、素材不足、実案件整理の改善。
   - references/01_research_evidence.md: 新しい公式情報、事例、根拠の追加。
   - references/02_content_playbook.md: 制作ルール、フォーマット、分析手順の改善。
   - references/03_quality_and_update.md: 品質ゲート、不合格条件、更新手順の改善。
   - references/04_account_strategy.md: アカウント戦略、競合/代替、リソース制約、訴求設計の改善。
   - references/05_profile_funnel.md: プロフィール、bio、ピン留め、ハイライト、リンク導線の改善。
   - references/06_monthly_operation.md: 月間運用、30日カレンダー、週次ルーティンの改善。
   - references/07_insight_analysis.md: インサイト分析、投稿改善、月次振り返りの改善。
   - references/08_industry_profile_patterns.md: 業種別プロフィール型の改善。
   - references/09_reels_script_matrix.md: リール台本量産表の改善。
   - examples/good-output.md: 出力型の改善。

2. 採用してよい材料だけを使う。
   - ユーザー提供の実例。
   - 実ファイル、実行ログ、インサイト数値。
   - 公式情報、公開事例、出典付きプロ事例。
   - A/Bテスト、レビュー結果、改善前後の比較。

3. 採用してはならない材料を除外する。
   - 出典のない噂。
   - 今回だけの好み。
   - 感情的な注意文。
   - 検証していないプロンプト。
   - 別案件では危険な固有ルール。

4. 再利用できる作業ルールへ変換する。
   - 根拠。
   - 良かった点。
   - 採用するルール。
   - 使える条件。
   - 使ってはいけない条件。

5. 最小のファイルだけを更新する。
   - 複数ファイルを同時に大きく書き換えない。
   - 旧ルールを消す時は、明確に悪化または矛盾している場合だけにする。

6. 更新後に必ず検証する。
   - 投稿制作シナリオを1つ実行する。
   - 素材不足の異常系シナリオを1つ実行する。
   - 発火条件、参照ファイル、品質ゲートが機能するか確認する。

## 採用済み改善ルール

新しい改善を恒久ルールにする時だけ、この表へ追記する。

| 根拠 | 採用ルール | 使える条件 | 使ってはいけない条件 |
|---|---|---|---|
| 旧SNSスキル | DM共有、保存、視聴維持、コメント深度を重視する | 投稿企画、リール、カルーセル、分析 | 数値未確認で順位付けを断定する場合 |
| from-simeji品質基準 | スキル本文は短く、詳細はreferencesとexamplesへ分ける | スキル作成、更新 | 参照タイミングがSKILL.mdにない場合 |
| 辛口レビュー: 月間カレンダー例の不足 | 月間カレンダーは30行以上で出し、例も30日分に揃える | 月間運用、投稿カレンダー | ユーザーが明示的に短縮版を求めた場合 |
| 辛口レビュー: Step 2の混在 | 成果物の種類と投稿フォーマットを分けて選ぶ | 全ワークフロー | 投稿単体依頼で成果物選定が不要な場合 |
| 辛口レビュー: 初回ヒアリング欠損 | 初回、情報不足、実案件ではヒアリングシートを使う | 初回相談、プロフィール、月間運用、分析 | ユーザーが十分な入力をすでに渡した場合 |
| 辛口レビュー: 素材ゼロ日の欠損 | 素材レベルA/B/Cを判定し、撮影不可時の代替フローを出す | 月間運用、リール、カルーセル | 実績や顧客の声を架空で補う場合 |
| 辛口レビュー: ソース信頼性 | ツール販促色が強い記事は主要根拠から外す | 調査根拠、プロフィール設計 | 公式情報や実インサイトで裏取りできない場合 |
