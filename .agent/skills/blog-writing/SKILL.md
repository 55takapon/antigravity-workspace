# blog-writing

> ジェットプロデュース専用ブログ記事執筆スキル。読者目線×SEO最適化×AI検索引用設計を統合。

---

## ⚠️ 実行フロー（全体像・省略禁止）

```
STEP -1: 【音声文字起こしがある場合のみ】音声素材インテークを実施する
         （クレンジング→7項目の素材抽出→ブリーフ草案→文体変換ガイド）
         ※ 詳細手順: references/transcript-intake.md
         ※ 音声がない通常の記事はこのSTEPをスキップしてSTEP 0から開始
  ↓
STEP 0: SERP分析を実施する（上位3〜5記事の見出し・共起語・情報ギャップを確認）
        ※ 音声起点でもKW・検索意図はここで裏取りする（音声から推測しない）
  ↓
STEP 1: コンテンツブリーフ（17項目）を作成する ← 省略禁止
  ↓
STEP 2: 構成フレームワーク（PREP/PAS/AIDA）を選択し、見出し構成を確定する
  ↓
STEP 3: 以下の「執筆ルール」を守りながら本文を執筆する
  ↓
STEP 4: 執筆完了後、必ず /blog-writing-qa を実行して品質検査を受ける
  ↓
STEP 5: blog-writing-qa の判定が「PASS」になって初めて完了報告を行う
         ※ CONDITIONAL PASS は軽微修正後に再検査
         ※ FAIL は修正してSTEP 4 からやり直し
         ※ 判定なし・PASS未確認での完了報告は禁止
```

## プロンプト仕様（全記事共通コンテキスト）

### Role（書き手の役割定義）

```
あなたは、店舗・クリニック・士業事務所・整体院のオーナーと
日常的にやり取りしている「Web集客の専門家」です。

- Googleビジネスプロフィール・SNS・HPを連携した集客設計を専門とするプロデューサー
- 加古川・姫路・明石・神戸エリアを中心に全国対応
- 「良いサービスが、正しく見つけられる世の中に」がミッション
- オーナーの隣に座って一緒に考える「伴走者・相談相手」の立場
- 上から教える「先生」ではない
```

### Target Audience（読者の定義）

```
- 店舗・クリニック・士業・整体院のオーナーまたは経営者
- マーケティングの専門知識はほぼゼロ
- SEO、MEO、GBP、CTR等の用語を知らない
- 「集客に困っている」「何から手をつけていいかわからない」状態
- スマホで移動中・隙間時間に読む
- 「広告費をかけないと集客できないのか」という不安を持つ
```

## コンテンツブリーフ（17項目）

> 詳細テンプレートと記入例: `references/content-brief-template.md`

```
【基本情報】
1.  記事タイトル（案）: ___
2.  メインキーワード: ___
3.  サブキーワード（2〜3個）: ___
4.  対象業種（単一指定）: 店舗 / クリニック / 士業 / 整体院 / その他
    ※ クリニック・整体院指定時: 薬機法注意フラグ 🔴 ON
5.  検索意図: Know / Do / Go / Buy
6.  ターゲット読者の具体像: ___
7.  読者のペインポイント: ___
8.  読後のゴール: ___
9.  構成フレームワーク: PREP / PAS / AIDA
10. 見出し構成（H2/H3）: ___
11. 内部リンク先（2〜3本）: ___
12. 共起語・関連語リスト（STEP 0で収集）: ___
13. 上位競合記事の要約: ___
14. この記事独自の要素・情報ギャップ: ___
15. 想定される反論・不安（3つ以上。CV前に読者が迷うこと）: ___
16. CTA（検索意図別に選択）: ___
17. メタディスクリプション（80〜120文字）: ___
    + リライト管理（順位・CTR・AI引用・CVの判断基準）: ___
```

## 構成フレームワーク（概要）

> 詳細・CTA選択表・画像指針: `references/frameworks.md`

| フレームワーク | 適用記事 |
|-------------|---------|
| PREP | ハウツー・解説記事（Know/Do意図） |
| PAS | 課題解決・提案記事（Know意図） |
| AIDA | 事例記事（カテゴリF・Buy/Know意図） |

**AI検索パッセージ設計（全フレームワーク共通）**:
各H2の直下に「その見出しの問いに2〜3文で自己完結的に答える」文を必ず置く。その後に詳細を続ける。これにより AI検索エンジンに引用されやすい「パッセージ」が生まれる。

## 執筆ルール

> 禁止表現・用語言い換え・断言境界: `references/common-rules.md`

### 本文ルール（8か条）

1. **一文一義**: 1つの文に情報を詰め込まない（60文字以内）
2. **「あなた」の文章**: 「あなたのお店では〜」と語りかける
3. **「なぜ」を必ず添える**: やり方だけでなく理由を書く
4. **次を読みたくなる仕掛け**: セクション末尾で次への興味を引く
5. **具体的なアクション**: 「やりましょう」ではなく「○○の画面を開いて〜」まで書く
6. **断言境界を守る**: 手順・事実は断言する。集客成果・健康効果は断言しない
   → 境界の詳細は `references/common-rules.md` を参照
7. **強調は「\*\*」を使わない**: 強調は文章構成・語順・短文独立で表現する
8. **現場エピソードを1つ以上入れる**:
   「○○市の△△オーナーから実際にこう聞かれた」等の匿名化した一次情報を必ず入れる。
   AIが書いた一般論との差別化が目的。（ノウハウ記事・事例記事どちらも必須）
   エピソードは `references/primary-info.md` の未使用ストックまたは新規素材から選び、
   使用後は同ファイルの使用台帳に記録する。**エピソードの使い回しは禁止**（数値と同様）。

### 導入の書き方

以下の4要素を必ず含める。ただし冒頭の「型」は毎回同じにしない（全記事同型化の防止）。

```
【導入の4要素】
1. 悩みの言語化: 読者の状況や悩みを言語化する（冒頭400文字以内）
2. 共感: 「その気持ちわかります」と寄り添う
3. ベネフィット: この記事で何がわかるか
4. 結論の予告: 結論を1〜2行で示す（AI検索の直接回答として機能）
```

**冒頭の型は3種をローテーションする**（直近の公開記事と同じ型を連続で使わない）:
- 問いかけ型: 悩みを質問形で言語化して始める（基本形）
- エピソード型: 現場の相談場面から始める
- 結論先出し型: 意外な事実・結論を先に置いて始める

実例: `references/intro-examples.md` を参照。

**上級テクニック「偏見・嫌な記憶の代弁」**: 読者が持つネガティブな先入観をそのまま言語化する手法。
実例: `references/intro-examples.md` を参照。

### FAQのルール

最低3問。出典は **PAA / サジェスト / 現場の実質問** のいずれか。創作FAQ禁止。

### CTAブロックのルール（オファー設計）

CTAは「置く」だけでは行動されない。オファー名だけのCTA（「30分無料診断はこちら」等）は禁止。
記事末尾のCTAブロックは必ず次の3要素で構成する。
書き方の詳細と記入例: `references/frameworks.md` の「CTAブロックの書き方」

```
1. ブリッジ文: 記事の内容とオファーを橋渡しする1〜2文
2. オファー価値の言語化: 受け取ると何が手に入るかを具体的に書く
   （例: 「あなたのお店がマップで何位に表示されているか、どこを直せば
   見つけてもらいやすくなるかを、その場で一緒に確認します」）
3. 不安解消の一文: 「売り込まれるのでは」という警戒を先回りして解く
   （例: 「診断を受けたからといって、契約をおすすめすることはありません」）
```

ボタン文言（マイクロコピー）は「行動＋手軽さ」で書き、行動のハードルを下げる。
詳細: `references/frameworks.md` の「マイクロコピーと行動ハードル」

### 反論処理（CV前の不安を先回りで潰す）

ブリーフ15番の想定反論（「本当に必要？」「費用対効果は？」「自分の店に合う？」等）に、
本文内で必ず答える。答え方の型（比較表・向いている人/向いていない人・FAQ統合）と配置ルール:
`references/frameworks.md` の「反論処理の設計」を参照。
最低1つは「CTAブロックの直前」に置く（行動直前の迷いを潰してからオファーを出す）。

### 説得要素の使い分け（セールスライティング）

損失回避・社会的証明・権威性・Before/After・限定性は、**根拠がある場合のみ**使う。
使い分けと禁止例: `references/frameworks.md` の「説得要素ライブラリ」を参照。
根拠のない限定性・緊急性（偽の「今だけ」「残りわずか」）は禁止。

## 文字数の考え方

SERP分析で確認した上位記事の網羅性を基準に目安を決定する。
3,000〜5,000字は標準レンジ。**水増しでレンジに到達させることを禁止する**。
密度の低い記事はAI検索に引用されない。

## 実績データ利用ルール

記事タイプを問わず、根拠のある具体数値は使ってよい（ノウハウ系での数値禁止は撤廃）。
ただし以下2点を守る。

- **使い回し禁止**: 同じ実績数値を複数記事に流用しない。各記事ごとに固有の数値・事例を使う。
- **断言境界を守る**: 数値を出しても集客成果・健康効果は断言しない（詳細 `references/common-rules.md`）。

| 記事タイプ | 現場エピソード |
|-----------|------------|
| ノウハウ系（A〜E） | 匿名化したエピソード1つ以上（必須） |
| 事例記事（F） | 積極活用 |

## E-E-A-T・Helpful Content対応（Who / How / Why）

Googleが品質評価で問う「誰が・どう作り・なぜ公開するか」に、全記事が答えられる状態にする。

- **Who（誰が書いたか）**: 記事は「ジェットプロデュース（Web集客の専門家）」名義で公開する。
  入稿時に著者情報の表示を確認する（公開前チェックリスト参照）。
- **How（どう作ったか）**: 現場エピソード・一次情報が「実際の経験に基づく記事」の証明になる。
  AIによる一般論だけの記事を作らない（現場エピソード必須ルールの目的でもある）。
- **Why（なぜ公開するか）**: 検索エンジンのためだけの記事は書かない。
  ブリーフ8番「読後のゴール」が読者の課題解決になっていることが、公開する理由になる。
  読者の役に立たないままKWだけ狙った記事は、Helpful Contentの評価を下げサイト全体に悪影響が出る。

## 公開前チェックリスト（WordPress入稿後・人間が確認）

> ⚠️ これらはテキスト原稿では確認不能なため、QA採点対象外。入稿担当者が確認する。

```
□ パーマリンクを英語で設定した
□ アイキャッチ画像を設定した
□ 画像のaltタグにキーワードを含めた
□ SWELL整形（ふきだし・ステップ・FAQブロック・ボタン）を適用した
□ 内部リンクが正しくリンクされているか確認した
□ 著者情報（Who）が記事に表示されているか確認した
□ 公開日・更新日が表示されているか確認した
```

## NGパターン

- STEP 0（SERP分析）をスキップしてブリーフを作成する
- ブリーフ作成をスキップして執筆を開始する
- 対象業種を複数にする（1記事1業種）
- 専門用語をそのまま使用する（GBP、MEO、CTR等）
- 「〜という方は多いです」「いかがでしたか？」の使用
- ノウハウ記事・事例記事を問わず現場エピソードを1つも入れない
- 使用済みの現場エピソードを別記事で再利用する（primary-info.md の使用台帳で確認）
- CTAをオファー名だけ（「30分無料診断はこちら」等）で済ませる
- 直近の公開記事と同じ導入の型を連続で使う
- 水増しで文字数レンジに到達させる
