# Skill Creator

「スキルにして」「スキルを作りたい」と言われたら、
チャットの内容をもとにスキルを組み立てて、そのまま完成品を作る。
既存スキルを改善したい依頼ではなく、新規作成のときだけ使う。

## ステップ1: 会話を振り返る

ユーザーから指示を受けたら、まず今のチャット全体を必ず振り返り、以下を全て抽出すること:

- [ ] スキル化する対象の作業を特定した
- [ ] 作業の手順（ステップバイステップ）を抽出した
- [ ] 使用したツール・API・外部サービスを記録した
- [ ] 各ステップの入力と出力を特定した
- [ ] 判断ポイント（条件分岐）を特定した
- [ ] エラーや注意点を記録した
- [ ] スキルに入れる再利用ルールと、今回だけの作業指示を分けた
- [ ] ユーザーが作業者へ向けた一時的な注意を、そのままスキル本文に入れていない
- [ ] ユーザー提供例、生データ、公式資料、公開されているプロ事例、ローカル実ファイルの有無を確認した
- [ ] 成功例、改善前後、A/B結果、レビュー結果、実行ログがある場合は、再利用できる成功法則を抽出した
- [ ] 検索や公式資料確認が必要な内容は実際に確認し、確認できない内容は未確認として分けた
- [ ] 比較検証の手順、検証者の作業メモ、今回だけの注意をスキル本文に混ぜていない

#### 完了条件
- 上記全項目にチェックが入っていること
- 既存スキル改善ではなく新規作成依頼であること。改善依頼なら `skill-update` に必ず委譲する
- 作業者だけに向けた注意と、スキルへ入れる再利用ルールが分かれていること
- 使った材料と未確認の材料が分かれていること
- チェックが入らない項目がある場合、ステップ2で質問する
- この完了条件を全て満たすまで、次のステップに進んではならない

---

## ステップ2: 不足情報の質問

ステップ1で埋められなかった項目について、ユーザーに質問する。
質問は一度にまとめて出し、ユーザーの負担を最小化する。

例えば以下のような質問:
- この作業はどういう時にやるものか?
- 出来上がりの良し悪しはどこで判断する?
- 具体的に「こんな入力 → こんな出力」の例はあるか?
- 参考にする実データ、ユーザー提供例、プロ事例はあるか?
- 公式資料や公開事例を確認する必要がある作業か?
- 使うツールやサービスにログイン等は必要か?

#### 完了条件
- ステップ1の全項目が埋まっていること
- ユーザーが質問に回答済みであること
- この完了条件を全て満たすまで、次のステップに進んではならない

---

## ステップ3: 材料と品質基準を確認する

作る前に、今回のスキルに必要な材料と品質基準を必ず確認すること。
構造と品質基準を決めるため、この工程で [references/skill-quality-standards.md](references/skill-quality-standards.md)、[references/skill-structure-guide.md](references/skill-structure-guide.md)、[references/prompt-quality-guide.md](references/prompt-quality-guide.md) を読む。複雑スキル、文章生成スキル、プロンプト生成スキル、生データやプロ事例が必要なスキルでは [references/pro-skill-writing-examples.md](references/pro-skill-writing-examples.md) を必ず読む。成功例、改善前後、A/B結果、レビュー結果、実行ログを使う場合は [references/success-pattern-guide.md](references/success-pattern-guide.md) を読む。出力構造に迷う場合だけ [examples/good-skill-structure.md](examples/good-skill-structure.md) を読む。

- [ ] ユーザー提供例、生データ、公式資料、公開されているプロ事例、ローカル実ファイルのどれを使うか確認した
- [ ] 検索が必要な内容は検索し、公式資料または公開されている実物を確認した
- [ ] 既存スキルを参照する場合は、ユーザー指定または今回の作業に直接関係する実ファイルだけに限定した
- [ ] 成功法則を使う場合は、根拠となる実物、採用する理由、使える条件、使ってはいけない条件を分けた
- [ ] `references/skill-quality-standards.md` を `view_file` で読んだ
- [ ] `references/skill-structure-guide.md` を `view_file` で読んだ
- [ ] `references/prompt-quality-guide.md` を `view_file` で読んだ
- [ ] 複雑スキル、文章生成スキル、プロンプト生成スキル、生データやプロ事例が必要なスキルでは `references/pro-skill-writing-examples.md` を `view_file` で読んだ
- [ ] 成功法則を使う場合は `references/success-pattern-guide.md` を `view_file` で読んだ
- [ ] `examples/good-skill-structure.md` を `view_file` で読んだ

#### 完了条件
- 使う材料、使わない材料、未確認の材料が分かれていること
- プロ事例と呼ぶ材料は、実物を確認済みであること
- 成功法則を使う場合は、根拠、採用理由、適用条件、除外条件が分かれていること
- 品質基準、構造ガイド、プロンプト品質基準を把握済みであること
- 複雑スキル、文章生成スキル、プロンプト生成スキル、生データやプロ事例が必要なスキルでは、プロ粒度の見本を把握済みであること
- この完了条件を全て満たすまで、次のステップに進んではならない

## ステップ4: SKILL.md + 分離ファイルの生成

公式推奨構造に従い、`SKILL.md` と分離ファイルを作る。
この工程では、置き場所の判断基準として [references/skill-structure-guide.md](references/skill-structure-guide.md) を必ず参照すること。

- [ ] `SKILL.md` には、入口、手順、各工程で読む資料、エッジケース、禁止事項、自己完了確認だけを書いた
- [ ] 詳しい判断基準、品質基準、工程別の詳しい作業内容、粒度見本は `references/` に分けた
- [ ] 実際の入力と出力、または実データがない時の出力の型は `examples/` に分けた
- [ ] 長い原文、生データ、ユーザー提供素材は、必要に応じて `knowledge/` に分けた
- [ ] 工程で使う詳しい型は、その工程の `references/` から読める形にした
- [ ] 完成形を見せる出力例や出力の型は `examples/` に置いた
- [ ] A/B検証者の作業手順や今回だけの会話上の注意を、作成されるスキル本文へ混ぜていない

### 品質チェック（書き出す前に全て確認。1つでも未確認なら書き出してはならない）

- [ ] SKILL.md本体が2,000トークン以下か?（文字数÷4で概算）
- [ ] 詳細ルール・判定テーブルがSKILL.md内に残っていないか?
- [ ] 具体例がexamples/に分離されているか?
- [ ] references/への参照ナビゲーションが、該当工程の中にあるか?
- [ ] 会話中の今回だけの注意を、スキル本文に混ぜていないか?
- [ ] 比較検証の手順や検証者の作業メモを、スキル本文に混ぜていないか?
- [ ] 使った材料と未確認の材料を分けているか?
- [ ] プロ事例は実物確認済みか?
- [ ] 見出しが短すぎる名詞だけになっていないか?
- [ ] 不自然な日本語見出しが残っていないか?
- [ ] 標準では作らない補助ファイルを増やしていないか?
- [ ] プロンプト系の成果物が、タグ形式ではなくMarkdown文書として自然に読めるか?
- [ ] プロンプトやテンプレートに、未完成の穴埋めや省略記号が残っていないか?
- [ ] プロンプト系の成果物が、何をするか、使う材料、判断基準、出力形式、確認方法まで含む実行可能な本文になっているか?
- [ ] 複雑な工程の `references/` が、浅い3〜5手順だけで終わっていないか?
- [ ] 中核工程の参照資料が、品質に必須なのに任意扱いになっていないか?
- [ ] references/skill-quality-standards.md の全基準を満たしているか?
- [ ] スキップ防止パターンを適用したか?（義務表現・ゲート条件・自己完了確認）
- [ ] 既存スキルの品質水準に達しているか?

#### 完了条件
- 上記全項目にチェックが入っていること。1つでも欠けている場合は書き出してはならない
- SKILL.md + references/ + examples/ をファイルとして書き出し済み
- この完了条件を全て満たすまで、次のステップに進んではならない

## ステップ5: references/ と examples/ の生成（必須）

以下を必ず生成すること:

1. **examples/good-output.md** — 入力→出力ペア最低2つ（正常系+異常系）
2. **references/** — SKILL.mdから分離した詳細ルール・判定基準
   - ファイル名はスキル内容に合わせて命名
   - 複雑な工程がある場合は `references/01_依頼整理.md` のように工程順で分ける

生成したら、SKILL.md内の該当工程に参照リンクを必ず追加すること。
冒頭で全ファイルを読ませるのではなく、該当工程内で読むタイミングを明示する。補助資料なら「この工程で必要なら読む」でよい。複雑スキルの中核工程で、その参照資料が品質に必須なら「この工程では必ず読む」と書くこと。

### 分離不要の例外

SKILL.md本体が80行以下で、判断ルール・表記ルール・品質基準・ツール仕様・プロ事例・生データがない場合のみ、references/ は省略可。
ただし examples/good-output.md は必ず生成すること。

### 具体例の扱い

- ユーザー指定の実例や生データがある場合は、スキルが直接読む `examples/` または `knowledge/` に置く
- 文章、投稿、文体、マーケティング系では、作成者が想像した完成文を良い例として置かない
- 実データがない場合は、コピーできる完成文ではなく、入力項目や出力の型だけを示す
- プロ事例は、検索、公式資料、ユーザー提供例、ローカル実ファイルのいずれかで実物を確認した場合だけ使う
- `プロ事例` と呼ぶファイルには、参照元名、出典パスまたはURL、実本文または実際のプロンプト本文を必ず入れる
- 出典と本文がない抽象メモは、プロ事例ではなく `references/` の型や確認基準として扱う
- 実在するプロ事例がない場合は、プロ事例ありとして進めず、出力の型だけを示す
- 材料が足りない場合は、具体例を作り込まずステップ2へ戻って質問する
- プロンプトやテンプレートを出す場合は、Markdownの見出し、箇条書き、表で読める形にする
- プロンプトやテンプレートを出す場合は、そのまま実行できる本文にし、未完成の穴埋めや省略記号を残さない
- 複雑な工程の `references/` は、プロ粒度の見本と比べ、浅い手順だけで終わっていないことを確認する

#### 完了条件
- examples/ が生成済みであること
- references/ が生成済みであること（例外条件に合致する場合を除く）
- 具体例が、実データ・ユーザー提供例・プロ事例・出力の型のいずれかであること
- プロ事例は実物確認済みであり、出典と本文が分かること
- プロンプト系の成果物がある場合、Markdown文書として自然に読めること
- 複雑な工程の `references/` が、プロ粒度の見本と同じ深さで書けていること
- SKILL.md内に、必要な工程で読む参照ナビゲーションが含まれていること
- この完了条件を全て満たすまで、次のステップに進んではならない

## ステップ6: テスト（省略禁止）

生成したスキルに対して必ず Skill Checker を実行すること。テストを省略して完了報告してはならない。

- [ ] Skill Checker の SKILL.md を必ず読み込むこと
- [ ] Skill Checker の全チェックを必ず実行すること
- [ ] 全項目が pass になっていること（failは修正→再チェック済み）
- [ ] 検証時は、skill-creator入口、読んだ資料、生成先、Skill Checker結果を報告に残した
- [ ] スキルの保存先が `C:\Users\hangy\.gemini\antigravity\.agent\skills\[スキル名]` であり、命名が skill-management の命名規則に従っていることを確認した
- [ ] skill-management の SKILL.md「現在のスキル一覧」テーブルに新スキルの行を必ず追加した

テスト結果を必ずユーザーに報告すること。

## 禁止事項

- 会話を分析せずにスキルを生成してはならない（ステップ1必須）
- ユーザーへの質問をスキップしてはならない（不足情報がある場合）
- 既存スキルを読まずに生成してはならない（ステップ3必須）
- 既存スキルの改善依頼をこのスキルで処理してはならない（`skill-update` を使う）
- 品質チェックをスキップしてはならない
- 生成物だけを作り、どの入口・資料・チェックで作ったかを残さずに完了してはならない
- 検索や公式資料確認が必要な内容を、未確認のまま確認済みとして扱ってはならない
- YAML frontmatterのname/descriptionを省略してはならない
- テストを実行せずに完了報告してはならない
- skill-management の「現在のスキル一覧」テーブルを更新せずに完了報告してはならない
- 義務表現のない必須ステップを含むスキルを生成してはならない
- SKILL.md本体に詳細ルール・判定テーブル・具体例を直接書いてはならない
- ユーザーが作業者へ向けた今回だけの注意を、スキル本文にそのまま入れてはならない
- 作成者が想像した完成文を、実例や良い例として置いてはならない
- 出典や本文を確認していないものを、プロ事例として置いてはならない
- `prompt-index.md` と `prompt-quality-requirements.md` を標準ファイルとして作ってはならない
- プロンプト系の成果物を、標準で山括弧タグ、JSON、YAMLだけの読みにくい形式にしてはならない
- 「役割」「目的」「使う材料」「出力形式」などを、自然なMarkdown見出しにできるのに独自タグへ逃げてはならない
- 比較検証の手順や検証者の作業手順を、スキル本文へ混ぜてはならない

## エッジケース

| 状況 | 対応 |
|:-----|:-----|
| 会話が短すぎてスキル化に必要な情報がない | ユーザーにその旨を伝え、もう少し作業してから再度依頼を促す |
| 同名のスキルが既に存在する | 上書きするか別名にするかユーザーに確認 |
| 作業がシンプルすぎてスキルにする価値がない | 「ワークフロー(.md)の方が適切では？」と提案 |
| scripts/が必要だが依存パッケージがある | SKILL.md本文に依存を記載（frontmatterに非公式フィールド `dependencies` を書かない） |
| SKILL.mdが80行以下で判断ルールも表記ルールもない | references/は省略可。ただしexamples/は必須 |
| 簡単な作業だが判断基準や表記ルールがある | references/を作り、該当工程から読む形にする |
| 会話中に作業者への注意が多い | 再利用できる作業ルールだけに絞り、今回だけの注意は入れない |
| 実例や生データが足りない | 想像で完成例を作らず、必要な材料を質問する |
| 公式資料や公開事例の確認が必要 | 検索や実ファイル確認を行い、確認できた材料だけを使う |
| ユーザーがタグ形式を明示している | ユーザー指定を確認した上でだけ使う。指定がなければMarkdownにする |
