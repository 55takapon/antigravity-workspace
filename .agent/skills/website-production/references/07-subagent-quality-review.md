# サブエージェント品質レビュー

## 目的

構築後に、制作者本人とは別の視点で、トップページの品質を確認する。セルフチェックだけでは見落としやすい、テンプレ感、文字量過多、ファーストビューの弱さ、レスポンシブ崩れ、コード品質の甘さを検出する。

## 実行条件

- HTML/CSS/JSなどの実装ファイルを作成した場合は、このレビュー工程を必須にする。
- サブエージェント、レビュー担当、別視点の検証ツールが使える環境では、構築後に必ず品質レビューを依頼する。
- サブエージェントを使えない環境、または利用許可がない環境では、未実行理由を明記し、同じチェック項目で代替セルフレビューを行う。
- サブエージェントを使えるのに省略してはならない。時間短縮、軽微な案件、セルフチェック済みという理由では省略不可。
- 利用不可の例は、該当ツールが提供されていない、ユーザーがサブエージェント利用を明示的に禁止した、環境制約でレビュー対象ファイルを渡せない、などに限る。
- レビュー結果に重大指摘がある場合は、修正後に再確認または再レビューを行ってから完了報告する。

## レビュー担当へ渡す材料

レビューを浅くしないため、可能な範囲で次を渡す。

- 制作プロンプトまたは要件メモ
- 作成したHTML/CSS/JSなどの実装ファイルパス
- 使用画像の一覧と用途
- PC、タブレット、スマホの確認幅
- スクリーンショットがある場合はそのパス
- 既に分かっている未確認事項や残課題

## レビュー担当の役割

レビュー担当には、次の役割を与える。

```text
あなたは日本向けWebサイトに強いシニアアートディレクター兼フロントエンドレビュアーです。
制作済みトップページを、クライアントに提出する前の品質チェックとして辛口にレビューしてください。
良い点の列挙ではなく、提出前に直すべき問題、安っぽく見える要因、レスポンシブ崩れ、コード品質上の懸念を優先して指摘してください。
```

## レビュー観点

- ファーストビュー: 初見3秒で、誰の何をどう助けるサイトか分かるか。
- 画像の扱い: 主役画像が小さく扱われていないか。背景全面、大判写真、余白、トリミングが適切か。
- 文字量: ファーストビュー、カード、CTAまわりに説明やタグを詰め込みすぎていないか。
- 固有性: ロゴと社名を隠しても、業種、地域、提供価値、店や会社らしさが残るか。
- セクション造形: 白背景、中央見出し、薄いカード、均等3カラムの繰り返しになっていないか。
- 導線: CTAが見つけやすく、文言が心理段階に合っているか。
- レスポンシブ: PC、タブレット、スマホで、はみ出し、横スクロール、文字重なり、画像主役の切れがないか。
- 実装品質: HTMLが意味構造を持ち、CSSがトークン化され、不要な重複や場当たり的な指定が増えていないか。
- アクセシビリティ: 文字サイズ、コントラスト、ボタンのタップ領域、alt想定が最低限成立しているか。

## レビュー依頼プロンプト

```text
以下の制作済みトップページについて、提出前品質レビューをしてください。

レビューでは、良い点よりも修正すべき問題を優先してください。
制作プロンプト、実装ファイル、使用画像、確認幅、スクリーンショットがある場合は、それらを前提に確認してください。
特に以下を確認してください。

1. 初見3秒で、業種、対象者、提供価値、次の行動が分かるか
2. ファーストビューが弱くないか、画像が小さく扱われていないか
3. 文字量が多すぎないか、タグやバッジを詰め込みすぎていないか
4. 既製テーマ感、均等カード量産、白背景+中央見出しの繰り返しがないか
5. ロゴと社名を隠しても案件固有の印象が残るか
6. PC、タブレット、スマホで崩れ、はみ出し、横スクロールが起きそうな箇所はないか
7. HTML/CSS/JSがプロのコーダーとして提出できる品質か

出力は以下の形式にしてください。

## 重大指摘
- ファイル/箇所:
- 問題:
- 修正方針:

## 中程度の指摘
- ファイル/箇所:
- 問題:
- 修正方針:

## 軽微な指摘
- ファイル/箇所:
- 問題:
- 修正方針:

## 合格判定
- 提出可 / 修正後提出可 / 提出不可
```

## 合格条件

- 重大指摘が残っていない。
- ファーストビュー、文字量、固有性、レスポンシブ、コード品質の確認結果がある。
- サブエージェントを使えなかった場合は、理由と代替レビュー結果が報告されている。
