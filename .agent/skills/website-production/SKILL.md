# 🏗️ Webサイト制作スキル（本体）

日本向けWebサイトを、最低限のヒアリングから設計・画像素材・実装・品質確認まで進める統合スキル。

- **このフォルダが本体（正）。** Codex側 `C:\Users\hangy\.codex\skills\website-production-core` はこの本体へのリダイレクトスタブであり、内容の更新は必ずこちらで行う。
- 業種別・工程別の詳細は `references/` を該当工程で必要時だけ読む。
- 案件固有情報（金額・スケジュール・クライアント情報）は `clients/` に格納する。

## モード判定（最初に行う）

**案件種別**（デモ/受託）と**納品形態**（A/B/C）を最初に決める。

| 納品形態 | 内容 | 使うフロー |
|:---|:---|:---|
| **A. 静的サイト**（WordPressなし） | デモ、LP、更新ほぼ不要な店舗・会社サイト | コアフロー ステップ1〜5。受託で公開まで行う場合は [references/08-static-publish.md](references/08-static-publish.md) を必須 |
| **B. WordPress × SWELL** | 顧客が自分で更新する標準的な受託 | [references/10-wordpress-swell-project.md](references/10-wordpress-swell-project.md) の P1〜P12（デザイン・QA工程ではコアフローのreferencesを併用） |
| **C. WordPress オリジナル軽量テーマ** | シンプル設計＋ブログのみ。静的ファーストで作りテーマ化 | コアフローで静的版を完成 → [references/11-wordpress-original-theme.md](references/11-wordpress-original-theme.md) で変換（受託共通工程は10を再利用） |

### 納品形態の選定基準

| 判断軸 | A 静的 | B SWELL | C オリジナルテーマ |
|:---|:---|:---|:---|
| コンタクトフォーム | **不可**（必要ならB/Cへ） | ○ | ○ |
| 問い合わせ導線 | LINE公式・電話・GBP | フォーム＋LINE/電話 | フォーム＋LINE/電話 |
| 顧客が自分で更新 | しない | 固定ページも更新する | ブログのみ更新する |
| 保守契約 | 任意 | 任意 | **必須** |
| 向くケース | デモ・LP・低予算・短納期 | 受託の標準（迷ったらこれ） | シンプル設計でSWELL構築より静的コーディングが速い場合 |

**判定ルール:**
- **コンタクトフォームが必要ならWordPress（B/C）。** 静的サイトの問い合わせはLINE公式アカウント・電話・GBP導線とする。
- 迷ったらBに倒す。Cは [references/11-wordpress-original-theme.md](references/11-wordpress-original-theme.md) の採用条件を全て満たすときだけ選ぶ。
- どれか不明な場合は、ステップ1のヒアリングで「作る範囲」「更新するのは誰か」「フォームの要否」を確認してから決める。

## コアフロー

### ステップ1: 依頼内容と材料を整理する

必要資料: 依頼内容に不足がある場合は [references/01-intake.md](references/01-intake.md) をこの工程で必ず読む。

- [ ] ユーザーの目的、業種、作る範囲、成果物を特定する
- [ ] ユーザー提供素材、実ファイル、URL、未確認材料を分ける
- [ ] 新規制作やデモサイト制作では、作業開始前に案件ごとの新規プロジェクトフォルダ名を決める。例: `demo-cafe`, `demo-asian`, `demo-hair-salon`, `demo-seitai-clinic`, `client-xxxx-site`
- [ ] フォルダ名は英数字・ハイフン中心にし、日本語ファイル名や日本語フォルダ名は原則避ける
- [ ] 不足情報が制作品質に大きく影響する場合だけ、最小限の質問をする
- 入力: ユーザー依頼文、添付画像、ローカル素材、参考URL
- 出力: 材料カード、出力先プロジェクトフォルダ、質問または前提条件

完了条件: 材料カードがあり、確認済み材料と未確認材料が混ざっていないこと。実装を伴う場合は、出力先プロジェクトフォルダが決まっていること。この完了条件を満たすまで次に進んではならない。

### ステップ2: 業種別ルールを選ぶ

必要資料: 業種が分かる場合は該当する `references/industry-*.md` をこの工程で必ず読む。業種が曖昧な場合は [references/industry-generic.md](references/industry-generic.md) を読む。

- [ ] 業種に合う参照ファイルを1つ選ぶ
- [ ] 既存ジャンルにない場合は、汎用ルールを使い、今回の業種特性を材料カードへ追記する
- [ ] 業種の配色、写真、導線、避ける表現を決める
- 入力: 材料カード、業種名、参考素材
- 出力: 業種別デザイン方針

完了条件: 採用する業種ルールと、採用しない方向性が明確であること。この完了条件を満たすまで次に進んではならない。

### ステップ3: 画像素材を設計または生成する

必要資料: 画像生成、参考素材の扱い、JPG保存が必要な場合は [references/02-assets-images.md](references/02-assets-images.md) をこの工程で必ず読む。

- [ ] 素材を「そのまま使う画像」と「参考画像」に分ける
- [ ] サイト挿入用画像の枚数、用途、ファイル名、alt想定を決める
- [ ] 画像生成が必要なら、必要なツールを使って即座に自動実行すること。ユーザーへの確認は不要
- 入力: 素材カード、業種別方針、参考画像
- 出力: 画像指示、生成画像、保存パス

完了条件: 画像の用途、保存場所、使う/使わない理由が明確であること。この完了条件を満たすまで次に進んではならない。

### ステップ4: トップページ構成と制作プロンプトを作る

必要資料: 構成、ファーストビュー、導線、コンポーネント設計は [references/03-site-design.md](references/03-site-design.md) をこの工程で必ず読む。テンプレ感、安っぽさ、文字量過多、プロっぽさ、クリエイティブ品質が論点になる場合は [references/06-creative-direction-research.md](references/06-creative-direction-research.md) も読む。提案スライド用テンプレート集をWeb制作へ変換する場合は [references/05-template-conversion.md](references/05-template-conversion.md) を読む。

- [ ] ファーストビュー、主要セクション、CTA、フッターを設計する
- [ ] 制作者がそのまま使えるMarkdown形式の制作プロンプトにする
- [ ] 制作プロンプトの冒頭に、本体スキル（`website-production`）の必須使用と、読めない場合に構築を開始しないゲートを入れる
- [ ] 制作プロンプトの冒頭または実装条件に、出力先プロジェクトフォルダを絶対パスまたは作業ディレクトリからの相対パスで明記する
- [ ] 初見3秒で記憶させる内容、固有の視覚モチーフ、文字量制限、汎用3カラムカードを脱する具体ルールを制作プロンプトに入れる
- [ ] スライド用指示とWeb制作用指示を混ぜない
- 入力: 材料カード、業種別方針、画像素材
- 出力: Webサイト制作プロンプト

完了条件: 何を作るか、使う材料、出力先プロジェクトフォルダ、出力形式、確認方法、必須スキル使用ゲート、初見3秒の印象設計、固有の視覚モチーフ、ファーストビューの文字量制限、セクションごとの造形ルールが制作プロンプト内に含まれること。この完了条件を満たすまで次に進んではならない。

### ステップ5: 実装と品質確認を行う

必要資料: **受託案件およびデザイン品質が論点の案件では、実装に入る前に [references/09-design-orchestration.md](references/09-design-orchestration.md) を必ず読み、管理者＋サブエージェント分業（FV2〜3案コンペ→合意→デザインロック→2セクションずつ展開）で進める。一発生成で全ページを作らない。** 実装、レスポンシブ、表示崩れ確認が必要な場合は [references/04-implementation-check.md](references/04-implementation-check.md) をこの工程で必ず読む。実装ファイルを作成した場合は [references/07-subagent-quality-review.md](references/07-subagent-quality-review.md) も読む。受託の静的案件で公開・計測まで行う場合は [references/08-static-publish.md](references/08-static-publish.md)、オリジナルテーマ化する場合は [references/11-wordpress-original-theme.md](references/11-wordpress-original-theme.md) をこの工程の後に読む。

- [ ] 実装依頼なら、必要なツールを使って即座に自動実行すること。ユーザーへの確認は不要（ただしFVコンペの案選定はユーザー合意を取る）
- [ ] 品質モード（受託・デザイン重視）ではFVを2〜3案制作し、スクリーンショットで比較・合意後にデザインロックしてから下層を2セクションずつ展開する
- [ ] `index.html`, `style.css`, `script.js`, `images/` などは必ず決定済みの新規プロジェクトフォルダ内に作成する
- [ ] 実装前に作成予定パスを確認し、カレントディレクトリ直下、スキル直下、既存プロジェクト直下へ確認なしに作成・上書きしない
- [ ] 同名プロジェクトフォルダがある場合は、ユーザーが明示した既存フォルダなら対象ファイルを確認してから作業し、明示がなければ `demo-name-v2` のような別名フォルダを作るか確認する
- [ ] PC、タブレット、スマホの崩れ、はみ出し、横スクロールを必ず確認する
- [ ] ファーストビューの印象、文字量、固有性、通常セクションの造形差を確認する
- [ ] サブエージェントまたは別視点レビュー担当が使える場合は、構築後に品質レビューを必ず依頼する
- [ ] サブエージェントを使えない場合は、理由を明記し、同じ観点で代替セルフレビューを実施する
- [ ] 確認で不合格があれば修正してから報告する
- 入力: 制作プロンプト、画像素材、実装条件
- 出力: 実装ファイル、確認結果、残課題

完了条件: 実装物または制作プロンプトが完成し、出力先フォルダ、上書きしていないこと、表示確認結果、クリエイティブ品質確認、サブエージェント品質レビューまたは代替レビューの結果が報告できること。この完了条件を満たすまで完了報告してはならない。

## エッジケース

| 状況 | 対応 |
|:---|:---|
| 業種が未指定 | 汎用ルールで仮設計し、業種確定が必要な箇所だけ質問する |
| 素材が少ない | 参考素材として扱い、必要な画像生成プロンプトと仮素材を作る |
| 実在店舗の情報が未確認 | 未確認として分け、住所・営業時間・価格などは公開前差し替え前提にする |
| スライド用テンプレートが渡された | そのままスライドを作らず、Webサイト制作プロンプトへ変換する |
| 同名プロジェクトフォルダが既にある | 明示された既存フォルダなら中身を確認して作業し、明示がなければ別名フォルダを作るか確認する |
| 受託案件でお客様のコンテンツ提供が遅延 | 締切を書面で明示しリマインド。スケジュール影響を早期報告する |
| 修正が収束しない（修正沼） | 修正ラウンド上限（2ラウンド想定）を書面で事前合意し、超過分は追加費用を提示する |

## 禁止事項

- 海外テンプレートや汎用LPを丸写ししてはならない
- 写真をただ並べただけのサイト指示で終えてはならない
- 重要情報を画像内文字だけに依存してはならない
- 作り物の完成例を、実例やプロ事例として扱ってはならない
- 未確認の店舗情報を事実として断定してはならない
- スライド制作指示とWebサイト制作指示を混ぜてはならない
- 新規制作やデモサイト制作で、確認なしにカレントディレクトリ直下、スキル直下、既存プロジェクト直下へ `index.html` などを作成・上書きしてはならない
- 受託案件で本番環境へ直接作業してはならない（ステージング必須）
