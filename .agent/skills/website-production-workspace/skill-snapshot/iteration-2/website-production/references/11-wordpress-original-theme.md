# WordPressオリジナル軽量テーマ（静的ファースト変換）

## 目的

シンプルなコーポレートサイト・店舗サイトで、SWELLのブロックエディタで組むより静的コーディングの方が速い場合に、**コアフローで完成させた静的サイトをWordPressテーマへ変換**する。フルスクラッチのテーマ開発はしない。

## 採用条件（全て満たす場合のみ選ぶ）

- [ ] 機能要件が**ブログ（お知らせ）のみ**である。フォームが必要な場合もWordPressなのでCF7等で対応可
- [ ] 固定ページ（TOP・会社概要・サービス等）を**顧客が自分で編集しない**（文言修正は制作側が対応する運用で合意済み）
- [ ] デザインがシンプルで、静的コーディング＋テーマ化の合計がSWELL構築より速い見込みが立つ
- [ ] **保守契約とセットで受注する**（テーマの更新責任が制作側に移るため。保守なしならSWELLを選ぶ）

1つでも満たさない場合は納品形態B（SWELL）へ戻る。特に「顧客が固定ページの文言を頻繁に直したがるタイプ」なら、結局Bの方が総コストは安い。

## 大原則

- **静的ファースト**: まずコアフロー（ステップ1〜5）＋レスポンシブ確認で静的サイトを完成させ、顧客のデザイン承認を取ってからテーマ化する。テーマ化しながらデザイン調整をしない。
- **クラシックテーマ構成**にする。ブロックテーマ（FSE）、theme.json中心の構成は採用しない（学習・保守コストが利点を上回る）。
- **WPループを使うのはブログ関連のみ**。固定ページ相当はPHPテンプレートに直書きする。カスタム投稿タイプ、ACF等のカスタムフィールド依存は原則作らない。
- ブレイクポイントは静的段階から960px/600px（SWELL準拠）で組んでおく（[04-implementation-check.md](04-implementation-check.md)参照）。

## 変換手順チェックリスト

### テーマの骨格

- [ ] テーマフォルダ作成（`style.css` のテーマヘッダー、`screenshot.png`）
- [ ] `functions.php`: CSS/JSのenqueue、`add_theme_support('title-tag')`、`post-thumbnails`、メニュー登録、不要機能の削除（絵文字スクリプト等）
- [ ] `header.php` / `footer.php` へ共通部を分割（`wp_head()` / `wp_footer()` を必ず入れる）
- [ ] `front-page.php`: 静的トップページのHTMLを移植
- [ ] 下層ページ: `page-{slug}.php` または固有テンプレートで移植
- [ ] `404.php`

### ブログ側（隠れ工数の本体。ここを見積に必ず含める）

- [ ] `home.php` または `index.php`: 記事一覧（ページネーション含む）
- [ ] `single.php`: 記事詳細
- [ ] カテゴリ・アーカイブ表示（`archive.php`。不要なら一覧へ統合）
- [ ] **`the_content` 用CSS**: 顧客はGutenbergで書くため、見出し（h2/h3）、段落、リスト、表、画像、引用、ボタンの記事内スタイルを必ず用意する
- [ ] `add_editor_style()` で編集画面の見た目を実表示に近づける
- [ ] トップページの「お知らせ新着」を `WP_Query` で動的表示に差し替える
- [ ] 顧客が使ってよいブロックを標準ブロックに限定する運用ルールをマニュアルに書く

### SEO・公開

- [ ] SEO SIMPLE PACK等でtitle/meta/OGP管理（[10-wordpress-swell-project.md](10-wordpress-swell-project.md) P8のチェックリストを適用）
- [ ] 構造化データ（LocalBusiness等）をテンプレートへJSON-LDで記述
- [ ] GA4/GSC設定はP8と同様

### 受託共通工程の再利用

企画（P1）、コンテンツ収集（P3）、環境構築（P5）、確認・修正（P7）、公開・SEO（P8）、ツール導入・納品（P9）は [10-wordpress-swell-project.md](10-wordpress-swell-project.md) をそのまま使う。**P6（SWELL構築）だけをこのファイルの変換手順で差し替える。** P5のうちSWELL購入・ライセンス認証は不要。

## 禁止事項

- 静的サイトの承認前にテーマ化を始めてはならない（手戻りが二重になる）
- カスタム投稿タイプ・カスタムフィールドを「あると便利」で追加してはならない（要件にあるときだけ）
- ページビルダー系プラグインを混在させてはならない
- 保守契約なしでオリジナルテーマを納品してはならない

## 確認方法

- 静的版と表示が一致している（テーマ化で崩れていない）。
- 顧客がGutenbergで書いた記事（見出し・リスト・画像・表を含むテスト記事）が崩れず表示される。
- WP本体・プラグイン更新後の表示確認手順が保守内容に含まれている。
- 操作マニュアルに「編集してよい範囲はブログのみ、固定ページの修正は制作側へ依頼」と明記されている。

## 不合格時の対応

- テーマ化の途中でデザイン変更要望が出た場合は、静的版へ戻して修正・再承認してからテーマ化を続ける。
- ブログ記事のスタイル崩れは、顧客の書き方ではなく `the_content` CSSの不足として制作側で直す。
