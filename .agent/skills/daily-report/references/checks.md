# CHECK-1〜3 の記入基準と禁止パターン

## 目的

レポートの「漏れ」と「嘘」を防ぎ、トラブルを必ずスキル資産に変換する。

## CHECK-1: トラブル → スキル反映確認

本日発生したトラブル・つまずき・ユーザーの厳しい指摘を全件リストアップし、各項目を確認する:

- 対象スキルの本文またはreferences/に追記済みか
- 未反映 → レポート完成前に今すぐ反映する
- 対象スキルが存在しない → 新規スキル作成の要否を判断する
- NG_RULES.md に該当ルールとして登録済みか（When / What / How to verify の3条件で書く）
- 本日、NG_RULES.md の既存ルールに抵触した事象はなかったか（すり抜け検知）

**絶対ルール: NG_RULES.md への登録なしに「再発防止済み」と書いてはならない。**

## CHECK-2: 調べ直し・探し直しの再発防止

以下のパターンが1回でも発生したら、必ずスキルへ記録する:

| NGパターン | 具体例 |
|---|---|
| 同じ情報を複数回検索した | APIエンドポイントを2回以上調べた |
| 「どこに書いたっけ？」が発生した | ファイルパスが分からなくなった |
| 同じエラーで再度詰まった | 先週と同じエラーで止まった |
| 手順が分からず最初から調べた | セットアップ手順を毎回調べる |
| ツールの使い方を再確認した | コマンドオプションを毎回調べる |

**ルール: 同じ内容の調べ直しは2回目を許容しない。1回目で必ず記録・スキル化する。**
発生なしの場合は「本日は発生なし」と明記する（省略不可）。

## CHECK-3: 前回ピックアップ進捗確認

- 完了 → [x] にマーク
- 未着手・継続中 → 理由と次アクションを記載（持ち越し日数も書く）
- 漏れ発見 → 優先度を上げて本日対応

前回レポートがない場合（初回）は「初回レポートにつきスキップ」と明記する。

## DONEの重要度順の判定基準

1. ユーザーの指摘・トラブルが発生した作業（最重要。隠さず先頭に）
2. ユーザーが最も時間を使った作業（リクエスト数・セッション時間で判断）
3. 成果物が多い作業
4. 小ネタ・軽作業は最後（先頭に置いてはならない）

## INCIDENTの記載粒度

各INCIDENTには以下を必ず含める（1行で済ませてはならない）:

- **発生**: 何が起きたか（ファイル名・具体的内容）
- **ユーザーの指摘**: 原文の引用（指摘があった場合）
- **影響**: どんな実害があったか
- **原因**: なぜ起きたか（推測ではなく技術的な原因）
- **対処 / スキル反映**: どう直し、どのスキルのどこに反映したか
- **根拠数値**: 中止・変更判断を書く場合は数値必須（「重複率が高いため中止」ではなく「重複率XX%、新規YY件/投入ZZ件のため中止」）

## 記載の裏取りルール（NG_RULES移管分）

| ID | When（いつ） | What（何をする/しないか） | How to verify（検証方法） |
|---|---|---|---|
| B-04 | クライアント名・業種名を記載する時 | セッションの一次情報で必ず裏取りする。推測で記載しない。不明なら「未確認」と明記 | レポートの表記がセッションログ内の表記と一致すること |
| B-05 | 中止・変更判断を記載する時 | 根拠数値（重複率・成功率・件数等）を必ず記載する | 該当セクションに数値が1件以上含まれること |
| F-07 | レポートを作成する時 | 記憶・会話サマリーを情報源にしない。必ずcollectorを実行し、検出数をヘッダーに記載し、全セッションとDONEを照合する | 「検出セッション数」行が存在すること。なければ未実行とみなす |

## キーワード検出の運用

- INCIDENT候補の検出語は `config/incident-keywords.json` で管理する（スクリプト改修不要で追記できる）
- 誤検出しやすい語は同ファイルの `exceptions` に除外パターンを追加する
- 検出はあくまで候補出し。引用文（口コミ原文等）への誤ヒットは文脈確認のうえ理由付きで除外してよい
