# 採用結果の記録と継続改善

## 目的

生成した返信案がそのまま使われたか、どこを直されたかを構造化して蓄積し、クライアントプロファイルとスキル本体を実データで更新し続ける。「介入して修正ばかり」の状態を検知して止めるための仕組みであり、記録を省略するとこのスキルは改善されない。

## 使う材料

- クライアント別ログ: `C:\Users\hangy\.gemini\antigravity\.agent\clients\<クライアント名>\gbp-review\log.md`
- クライアントプロファイル: 同フォルダの `profile.md`
- 業種別の品質境界: [../examples/approved-replies.md](../examples/approved-replies.md)

## 記録タイミング

- 返信案を提出した時: 記録テンプレを添える（この時点ではまだ記録しない）。
- 採用・微修正・不採用の結果が分かった時: 必ず log.md へ追記する。

## log.md の記録形式

```markdown
## #{通し番号} — {対応日}

| 項目 | 内容 |
|:---|:---|
| 星評価 | ⭐×{N} |
| スタイル判定 | {型}（根拠1行） |
| 結果 | 採用（無修正） / 微修正 / 不採用（独自作成） |
| 理由タグ | {語彙から1〜3個。採用（無修正）の場合は「なし」} |

**口コミ原文:**
> {全文}

**生成案:**
> {提出した返信案}

**実際に投稿した返信文:**
> {最終文。無修正採用なら「生成案と同じ」}

**修正差分と気づき:**
- {どこをどう直されたか。無修正なら省略可}
```

## 理由タグの語彙（この中から選ぶ。新語彙は追加理由を添えて追記する）

| タグ | 意味 |
|:---|:---|
| style-mismatch | スタイル判定が誤っていた（例: 分析調で返して鏡返しが正解だった） |
| voice-mismatch | 語彙・文体・ブランドフレーズがクライアントらしくない |
| length | 長すぎる・短すぎる |
| closing | 締めの文言が合わない |
| temperature | 丁寧すぎる・カジュアルすぎる等、温度感の不一致 |
| overreach | 事実・効果への踏み込みすぎ（法規・個人情報リスクを含む） |
| other | 上記以外（自由記述を必ず添える） |

## KPIと集計

- **無修正採用率** = 採用（無修正）÷ 結果が分かった件数
- 結果が5件たまるごとに直近5件の無修正採用率を算出し、log.md 末尾の「集計」欄へ必ず追記する。

## skill-update を提案する条件（いずれか該当で必ず提案する）

- 直近5件の無修正採用率が60%未満
- 同じ理由タグが直近5件で3回以上
- 既存4型（鏡返し・エコーバック・専門家・クリエイティブリミックス）に当てはまらないスタイルを発見した
- 業種別ルールにない法規・規約リスクに遭遇した

提案時は、該当した条件・根拠となるログ番号・改善候補（プロファイル修正で済むか、reply-rules.md の変更が必要か）を1〜3行で示す。

## approved-replies.md への昇格

- ユーザー修正で確定した返信文が、既存実例にない品質境界（業種×状況の新しい線引き）を示す場合、該当業種の見出しの下へ「口コミ内容・承認済み返信・採用理由（仮説）・差分境界」の形式で追記する。
- 仮説を確定へ昇格する時は、ユーザーへ該当実例と採用理由を示して明示確認を取り、見出しを「採用理由（確認済み）」に変更し、確認日と確認方法を1行で記録する。返信が採用された事実だけでは、理由まで確認済みとみなさない。
- クライアント固有のボイス（そのクライアントにしか通用しない言い回し）は approved-replies.md ではなく、そのクライアントの profile.md へ記録する。

## profile.md の初期化（新規クライアント）

1. `clients\<クライアント名>\gbp-review\` フォルダを作成する。
2. profile.md に次を書く: 業種、地域、GBP正式名称、返信者の立場、SEO語方針（入れるか・入れる場合のSEO語セット）、文体メモ、文体サンプル（初回承認返信を第1号として全文貼る）、運用注意。
3. log.md を記録形式のヘッダだけで作成する。
4. ブランドフレーズは、実際の口コミ・投稿・ユーザー確認で実在を確認できたものだけ登録する。想像で足さない。

## 確認方法

- 結果が分かった件がすべて log.md に記録されている。
- 理由タグが語彙内から選ばれている（otherには自由記述がある）。
- 結果件数が5の倍数に達した時に「集計」欄が更新されている。
- 提案条件に該当した件で、skill-update の提案がチャットに残っている。

## 不合格時の対応

- 記録漏れが見つかったら、次の返信作成の前に遡って記録する。
- 提案条件に該当しているのに未提案の場合は、直ちにユーザーへ skill-update 起動を提案する。
- 理由タグが判別できない修正を受けた場合は、推測でタグ付けせず、ユーザーに修正意図を1問だけ確認する。
