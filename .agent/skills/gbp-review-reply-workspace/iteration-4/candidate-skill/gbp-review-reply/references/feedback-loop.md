# 採用結果の記録と継続改善

## 目的

確定した採否と修正理由を、個別案件、クライアント、業種、共通候補に分けて記録する。このファイルは承認ガバナンス用であり、通常の返信生成では読まない。

## 記録タイミング

- 初稿を出しただけでは結果を確定せず、記録テンプレも通常表示しない。
- ユーザーから採用、修正、不採用、投稿済みの連絡を受けた時だけclient `log.md`へ追記・更新する。
- 投稿済みの根拠がない文を`posted`にしない。採用事実と採用理由の確認事実を分ける。
- 頻度確認に含めるのは`final_approved`と`posted`の最終返信だけ。draft、rejected、代替案、翻訳、修正履歴は数えない。

## 返信記録状態

| 状態 | 意味 |
|:---|:---|
| draft | 初稿・検討中 |
| rejected | 不採用 |
| final_approved | 最終文が承認済み |
| posted | 投稿済みの根拠あり |

## 例レジストリ状態

返信記録状態とは別に管理する。通常生成が参照できるのは、適用条件を満たす`confirmed-good`と、ユーザー確認済みの`active / active-conditional`だけである。

| 状態 | 意味・遷移条件 |
|:---|:---|
| candidate | 未確認候補。通常生成で参照しない |
| pending-user-selection | ユーザー選択待ち。通常生成で参照しない |
| confirmed-good | ユーザーが全文を明示承認・修正確定 |
| active | 現行ルールで再審査済み。条件内で参照可能 |
| active-conditional | profile、業種、事実確認等の条件を全て満たす時だけ参照可能 |
| historical | 承認・投稿履歴だが現役模倣元ではない |
| deprecated | 現行安全核と衝突し、生成へ使わない |
| eval-only | 評価・工程制御専用。生成例へ使わない |

- candidateや外部記事由来文を自動でconfirmed-good / activeへ昇格しない。
- 状態変更には、対象全文、確認者、確認日、根拠、適用条件、不適用条件を残す。
- A35はcandidate設計上`active-conditional`を推奨するが、本番状態の変更前に統括・ユーザー確認を要する。

## 適用範囲 E / C / I / U

| 記号 | 範囲 | 扱い |
|:---|:---|:---|
| E | その1件だけ | 個別logへ記録し、一般化しない |
| C | そのクライアント | profileの制約・例として検討 |
| I | その業種 | 同業の独立した複数事例で再現後に候補化 |
| U | 全クライアント共通 | 複数クライアント/業種で再現し、旧版比較・独立QA後に候補化 |

初回はEから始める。Cで解決できる問題をI/Uへ上げない。件数や採用率だけで自動昇格しない。

## 理由タグ

失敗原因の記録には既存ログとの互換性を保つ次の最小群を使う。1件0〜3タグとし、同義語を増やさない。

| タグ | 意味 |
|:---|:---|
| unsupported-content | 事実・内心・原因・強度を口コミより追加した |
| focus-structure | 焦点、長さ、文の役割、反復が不適切だった |
| closing-voice | 感謝、締め、敬語、client voiceが不適切だった |
| action-accountability | 謝意・受け止め・確認・改善の対象や実行可能性が不適切だった |
| privacy-policy | 個人情報、診療、契約、規約等の公開リスクがあった |
| profile-source | profile、knowledge、承認状態、出典の優先順位を誤った |
| process-regression | 局所修正、二重返信、状態記録等の工程回帰があった |

旧22タグを含む既存ログは改変しない。必要な分析時だけ対応表を作り、新規ログで過去タグを捏造変換しない。

## log.md最小記録

- 星評価、口コミ原文
- 初稿、最終投稿文
- 状態、結果、返信日
- 修正差分、確認済み修正理由
- 理由タグ0〜3件、適用範囲E/C/I/U候補

## 共通スキル更新ゲート

1. K1〜K6に関わる重大エラー0件を採用率より優先する。
2. 単一クライアントの1〜5件だけで共通ルールを変更しない。
3. `skill-update`の同一評価セットで旧版比較し、回帰0を確認する。
4. 独立QAとskill-checkerを通す。
5. クライアント固有の本文、店名、地域、商品、voice、窓口を共通スキルへコピーしない。

修正指示を受けた時は直前案へ継ぎ足さず、元の口コミ、profile、確定指摘から全文を再構成する。
