## 実装前の必須修正4点

### 1. 27ケースを「将来の良好全文例27件」にできる状態へそろえる

W10〜W17は、**元記事の返信文はeval-only**でよい。しかしシナリオ自体まで`eval-only-source`にすると、良好全文候補は既存3 + 書き直し9 + gap7 = 19件に留まる。

次の二軸に分ける。

- 外部の元返信: `source-reply=eval-only`
- 同じ入力場面から新規作成する安全な全文: `case-state=candidate-rewrite`

これにより、元記事を模倣せず、27ケースすべてを個別承認可能な良好例候補にできる。

### 2. ユーザー確定QB19件を機能群別に移行する

最低限、次の5群へ分けて、`保持場所 / runtime参照 / 良好例ID / 削除条件`を記載する。

1. QB01〜QB07: 歓迎・自然な終止
2. QB08〜QB10: 謝罪・受け止め
3. QB11〜QB15: 低評価の感謝
4. QB16〜QB17: 実行可能な対応
5. QB18〜QB19: 感情・状態の補充禁止

証跡としての`quality-boundaries.md`は保持してよい。問題は、19件すべてを通常runtimeへ残すのか、例の不適用条件へ移すのかが未決定な点である。

### 3. 安全核K1を強度水増しまで明文化する

推奨表現:

> 口コミにない事実・感情・効果を作らず、明記された評価・感情の強度も上げない。

良好例で代替するS04、S06、R05、R10、R17、R19、R21でも、K1〜K6を先に適用する順序をrouter仕様へ明記する。例文が安全核を上書きしてはならない。

### 4. 評価ケースを増やす前に既存34件へ割り当てる

`EX-*` / `EV-*`の新名称をそのまま新規評価にしない。次の順に整理する。

1. 既存34件で検証できるものへ対応IDを付ける。
2. 27コーパスの個別承認は評価ケースではなく例文審査として扱う。
3. phrase-level NGは全出力横断の静的gateへまとめる。
4. 新規評価は既存34件で入力条件を代替できないものだけに限定し、追加理由と上限を事前記載する。
5. iteration-3の補助2件を再利用する場合は「34 + 補助2」と表記し、正式34件と混同しない。
