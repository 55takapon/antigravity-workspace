# 採用結果の記録と継続改善

## 目的

確定した採否と修正理由を、個別案件、クライアント、業種、共通候補に分けて記録する。単一クライアントの却下を共通ルールへ直結させず、重大エラー0件を採用率より優先する。

## 使う材料

- クライアントログ: `clients\<client>\gbp-review\log.md`
- クライアント制約: 同フォルダの `profile.md`
- 共通例の状態: [../examples/approved-replies.md](../examples/approved-replies.md)
- 旧版比較: `skill-update` が作る対象スキルのworkspace

クライアント固有の原文、返信、文体、店名、地域、商品、窓口は共通スキルへコピーしない。

## 記録タイミングと状態

- 初稿を出しただけでは、通常出力に記録テンプレを付けず、結果も確定しない。
- ユーザーから採用、修正、不採用、投稿済みの連絡を受けた時だけ `log.md` へ追記・更新する。
- 状態は `draft`、`rejected`、`final_approved`、`posted` を使う。
- 定型句・構造の頻度分析に含めるのは `final_approved` と `posted` の最終返信だけ。draft、rejected、代替案、翻訳、参考訳、修正履歴は数えない。

## log.md の記録形式

```markdown
## #{通し番号} — {対応日}

| 項目 | 内容 |
|:---|:---|
| 星評価 | {1〜5} |
| 状態 | draft / rejected / final_approved / posted |
| 結果 | 無修正採用 / 修正採用 / 不採用 / 未確定 |
| 返信日 | {YYYY-MM-DD / 未投稿} |
| 理由タグ | {定義済みタグを0〜3個} |
| 適用範囲 | E / C / I / U候補 |

**口コミ原文**
> {全文}

**初稿**
> {提出した返信案}

**最終投稿文**
> {確定文。未確定なら空欄}

**修正差分**
- {何を削除・変更したか。無修正なら「なし」}

**修正理由**
- {確認済みの理由。推測なら「未確認」と明記}
```

投稿済みの根拠がない文を `posted` にしない。返信が採用された事実と、採用理由が確認された事実を分ける。

## 理由タグ

同義タグを増やさず、次の語彙から選ぶ。該当しない時は既存タグの定義拡張で扱えるか先に確認し、新設理由を記録する。

| タグ | 定義 |
|:---|:---|
| semantic-inflation | 原文より評価・感情を強めた |
| unsupported-inference | 口コミにない事実、内心、原因、対応状況を推測した |
| empty-sentence | 感謝、反応、対応、必要な案内の役割がない文を足した |
| focus-selection | 拾う論点を誤り、主要点や不満を落とした |
| construction-repetition | 同一返信内で同じ動詞・機能文を重ねた |
| structural-repetition | 同時バッチまたは直近の最終返信で、同一・ほぼ同形の感情文や感謝→感情→締め等の機能骨格を連続反復した。標準的な歓迎締めの自然な偶発重複だけは含めず、珍しい類語への強制置換もしない |
| cta-pressure | 他商品・予約・割引・キャンペーン・同伴者指定等の販促CTA、または再来店の約束化・念押しが生じた。一般的な接客上の歓迎締めは含めない |
| brand-novelty | 口コミと無関係なブランド表現・販促情報を足した |
| length-mismatch | 口コミの情報量に対して長さが不釣り合いだった |
| unnatural-variation | 表現差を作るために「機会」「日」等の不自然な言い換えをした |
| closing-mismatch | ★5肯定本文の自然な歓迎締めを欠いた、★4・★5本文なしを店側感情・受領報告だけの1文で終えた、★4本文なしに改善姿勢がない、高リスク業種で再訪・再相談を促した、または未確認の地域文脈を締めに使った |
| gratitude-mismatch | 感謝がない、浅い、対象がずれた、または通常締めが情報受領中心になった |
| apology-mismatch | 謝罪の直接性または強度が、確認済み事実とseverityに合わなかった |
| empty-sincerity | 「真摯に受け止める」等が、見直す対象と確認・改善行動なしで終わった |
| action-vagueness | 確認・改善の対象または行動が不明、あるいは未確認で実行可能性がなかった |
| public-reassurance-gap | 第三者に問題の軽視、反論、責任回避、実行不能と読まれる不安が残った |
| patch-regression | 局所修正で別箇所を悪化・再発させた |
| source-conflict | 口コミ、profile、knowledge、履歴の優先順位を誤った |
| privacy-risk | 個人情報や診療・相談・契約関係を公開上拡張した |
| policy-risk | 規約、法規、効果保証、評価変更要求等のリスクがあった |
| voice-mismatch | 敬語、語彙、記号、文数などクライアントvoiceと不一致だった |
| internal-context-leak | 内部で持つ背景理解を「時間」「勇気」「心苦しい中」等として公開文へ直書きした |

上記は22タグである。1件につき0〜3タグを原則とし、症状より根本原因を優先する。Excel側の `apology-underweight` / `severity-mismatch` は `apology-mismatch`、`accountability-gap` は `action-vagueness` または `public-reassurance-gap`、感謝関連の同義タグは `gratitude-mismatch` へ統合する。`respectful-gratitude` 等の良好属性は失敗タグにしない。

## phrase-level境界状態

返信記録状態、適用範囲、phrase-level状態は別軸で記録する。

| 状態 | 定義 |
|:---|:---|
| confirmed-good | 条件内で使用できることをユーザー指示で確認した境界 |
| confirmed-ng | 指定条件では使用しないことを確認した境界 |
| limited-use | 限定された文脈と確認条件でだけ使える境界 |
| candidate | 評価・選定前の候補 |
| historical | 承認・投稿・検討の履歴だが現役模倣元ではない |
| superseded-intermediate | 後の判断で置換された中間案 |
| pending-user-selection | ユーザー選択まで現役化しない候補 |

境界記録には、状態、使用条件、理由、適用範囲E/C/I/U、確認日、確認根拠、Before→中間→Afterを残す。H12の通常締め案は `superseded-intermediate`、個別確認で追加経緯を受けた場面の同文は別条件の `limited-use` として扱う。候補30件の全文は `candidate` かつ `pending-user-selection` のままとし、自動昇格しない。

## 適用範囲 E / C / I / U

| 記号 | 範囲 | 扱い |
|:---|:---|:---|
| E | その1件だけ | 個別ログへ記録。一般化しない |
| C | そのクライアント | `profile.md` の制約・例・NG候補として検討 |
| I | その業種 | 同業の複数クライアントまたは独立した複数事例で再現し、業種節の変更候補にする |
| U | 全クライアント共通 | 複数クライアントまたは複数業種で再現し、旧版比較で悪化がない時だけ共通変更候補にする |

初回はEから始める。Cで解決できる問題はprofileで扱い、IやUへ上げない。件数だけで自動昇格させず、同じ原因か、異なる入力でも再現するか、既存ルールで防げないかを確認する。

Uへの反映は `skill-update` のフルフローで、複数業種を含む同一評価セットによる旧版比較、重大エラー0件、回帰なし、独立QAを満たした場合だけ行う。単一クライアントの1〜5件、直近の採用率、同一タグの回数だけで共通スキルを変更しない。

## KPIと見直し判断

優先順位:

1. 重大エラー件数（必須0件）
2. privacy-risk / policy-risk / unsupported-inference の発生件数
3. 修正後の回帰件数
4. 情報量、焦点、voice、構造の品質
5. 無修正採用率（補助指標）

採用率が低いだけでは共通更新を提案しない。まずEの入力差、Cのprofile不足、Iの業種境界、Uの共通欠陥の順に原因を切り分ける。重大エラーが1件でもあれば、採用率が高くても合格としない。

## approved-replies.md への反映

- 実際にユーザー承認または投稿された最終返信だけを登録候補にする。作成者が考えただけの文を承認済みにしない。
- 実例は匿名化し、`active` / `historical` / `deprecated`、適用条件、不適用条件、承認事実の根拠を付ける。
- `active` は現行ルールで再審査済みの品質境界だけ。承認済みでも現行ルールに反するものは `historical` または `deprecated` とし、生成の模倣元にしない。
- クライアント固有のvoiceと実投稿例は `profile.md` に置き、共通例へ昇格させない。
- 採用理由がユーザー確認済みでなければ、理由は仮説と明記する。

## profile.md の初期化・更新

新規クライアントは、ユーザーの承認後に `clients\<client>\gbp-review\profile.md` と `log.md` を別変更単位で作る。既存資料は削除・移動・要約上書きしない。

profileには、正式名称、業種、返信者、トーン、敬語、記号、文数傾向、販促CTAの許可条件、一般的な接客上の締め、地域文脈付き締めの検証情報と使用条件、SEO、名称・地域、特定語の使用条件、クライアント固有NG、外国語、低評価窓口、参照可能なknowledgeの節、再審査済み実投稿例を分けて記録する。投稿用SEO、固定フッター、競合分析、重点訴求を自動参照にしない。

## 修正指示を受けた時

直前案へ差分だけを継ぎ足さず、元の口コミ、現行profile、確定済みの指摘から全文を再構成する。全ハードエラーとprofile制約を再検査し、`patch-regression` がないことを確認してから提出する。

## 確認方法

- 状態、最終投稿文、返信日、承認理由を捏造していない。
- 頻度集計が `posted` / `final_approved` の最終返信だけを対象にしている。
- 定義済みタグとE/C/I/Uが使われ、単一事例をUへ上げていない。
- 重大エラー0件を採用率より優先した。
- 共通スキルへクライアント固有情報をコピーしていない。
