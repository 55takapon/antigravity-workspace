# 失敗ケースを更新し続ける手順

このスキルは、ユーザー指摘、修正済み投稿、品質チェックで見つかった再発パターンを蓄積して改善する。新しい失敗を見つけたら、スキル本体を肥大化させず、examples と references に分けて反映する。

## 更新対象の分け方

| 追加する内容 | 保存先 | 判断基準 |
|:---|:---|:---|
| 特定クライアントで起きた失敗表現 | `examples/failure-cases-*.md` | 固有本文を最小限にし、具体表現、悪い理由、安全な修正方向で記録する |
| 複数クライアントに共通する判定基準 | `references/01-check-axes.md` | 一般化して軸1〜軸8のどこかへ反映する |
| 医療・士業など業種固有の注意 | `references/02-industry-compliance.md` | 業種別に再利用できる場合だけ反映する |
| 出力形式の改善 | `examples/good-check-report.md` | 報告の見やすさ、合否、保留理由の型を改善する |
| 今回だけの作業指示や叱責 | 追加しない | 再利用できる作業ルールへ変換できないものは捨てる |

## 新しい指摘を受けた時の手順

1. 指摘本文から、失敗表現を短く抜き出す。
2. その表現が「未確認事実」「口コミ風」「季節・家庭状況・予定の決めつけ」「医療・士業広告」「誇大表現」のどれかに当たるか分類する。
3. 同じ失敗が既存examplesにあるか確認する。
4. ない場合は `examples/failure-cases-案件名.md` へ、次の形式で追加する。

```markdown
| 具体表現 | 何が悪いか | 安全な修正方向 |
|:---|:---|:---|
| 対象表現 | 未確認の口コミ、家庭状況の決めつけなど | 確認済み事実へ戻す、削除する、質問へ回す |
```

5. 同じ型の失敗が複数案件で出た場合だけ、`references/01-check-axes.md` の該当軸へ一般化して追加する。
6. 法令・広告規制に関係する場合は、`references/02-industry-compliance.md` へ入れる前に公的資料または専門家確認の要否を明記する。

## 修正済み投稿が出た時の手順

1. 修正前と修正後を並べる。
2. 修正が「確認済み事実へ戻した」「断定を弱めた」「削除した」「保留にした」「投稿目的型に合う冒頭へ変更した」「確認済み事実をベネフィット翻訳した」「CTAを投稿目的・意思決定段階に合わせた」「同月重複を避けるため企画を差し替えた」のどれかを記録する。
3. 成功例本文として丸ごと保存しない。使うのは修正の判断軸だけにする。
4. 良好事例本文をユーザーが選ぶ運用の場合は、選定前の本文を `good example` と呼ばない。

## 一般化してよい条件

- 2件以上のクライアント、または2回以上のユーザー指摘で再発している。
- 特定の店名、医院名、商品名を外しても判断基準として成立する。
- 軸1〜軸8のどこに入るか明確である。
- 追加すると、次回のチェック漏れが減る。

## 一般化してはいけない条件

- そのクライアントだけの事情、言い回し、ブランドトーンである。
- 事実確認できていないが、良さそうに見えるだけの表現である。
- 医療・法律・税務の判断を、確認資料なしで断定している。
- ユーザーの今回だけの指示を、そのまま恒久ルールにしようとしている。

## 更新後の確認

- `SKILL.md` が入口と工程ナビゲーションに留まっている。
- 詳細ルールは references にある。
- 具体例は examples にある。
- 未確認の成功例や作り物の完成投稿を、良い例として追加していない。
- ライブ反映前に、旧版とステージング版の差分を確認している。
