# Small Company Research スキル

小規模企業の「提案候補リスト」を作成するスキル。
業種ターゲティングはキーワードプロファイルで制御するため、業種ごとにスキルを分ける必要はない。

## 設計原則

### 原則1: ポジティブフィルター最優先

```
❌ 旧: 広く拾う → NGキーワードで弾く → 漏れる → 追加 → 永遠に繰り返す
✅ 新: キーワードHITした企業だけを候補にする → 非該当は業種名不問で除外
```

> [!IMPORTANT]
> **博報堂・NTT・野球団問題の根本原因**: キーワードHIT確認なしの無差別取り込み。
> 本スキルでは公式サイトクロール後にキーワードHITを必須判定し、`not_matched` は候補本体に残さない。

### 原則2: 事例記事内企業のノーチェック取り込み禁止

```
✅ OK: Web幹事など業種ポータルサイトからの候補収集
❌ NG: マーケティング成功事例・導入事例記事に登場する企業をノーチェックで抽出
```

ポータルサイト（Web幹事、比較サイト、カテゴリディレクトリ等）は候補発見の入口として有効。
問題は「成功事例」「導入事例」等の記事に登場する **事例対象企業** をキーワードHIT確認なしで取り込んでいたこと。
事例記事内の企業は提案対象ではなく事例提供側であり、文脈が根本的に異なる。

### 原則3: スクレイピングファースト・トークンゼロ

```
優先順位:
1. DOM解析（HTMLテーブル、dl/dt/dd、定義リスト）
2. 正規表現（従業員数・代表者名・資本金パターン）
3. リンクテキスト/URLパターンマッチ（フォームURL、会社概要ページ）
4. ──ここまでトークンゼロ──
5. AI/LLM（最終手段。会社概要が崩れている場合のみ。ページ全文は渡さない）
```

### 原則4: 品質チェックは工程内組み込み

```
❌ 旧: 書き込み後に別スキルで品質チェック（忘れる・スキップされる）
✅ 新: ワークフロー内の品質ゲートとして組み込み。通過しないと出力しない
```

### 原則5: キーワードは「分類」ではなく「根拠候補」

```
❌ 旧: matched_keywords でWeb制作/Webマーケ等に分類確定
✅ 新: matched_keywords は「この企業が対象である根拠」として保存。最終判定はリスト側で行う
```

ワード判定だけで業種確定すると雑になる。根拠候補として保存し、後工程で精査する。

## コア機能（MECE）

| # | 機能ID | 概要 |
|---|--------|------|
| 1 | `seed_collect` | ポータルサイト、検索結果、比較記事から企業名・候補URLを収集 |
| 2 | `official_site_resolve` | 公式サイトURLを確定 |
| 3 | `profile_page_find` | 会社概要・企業情報・About・Profileページを探索 |
| 4 | `company_fields_extract` | 代表者、資本金、従業員数、所在地、事業内容、サービス内容を抽出 |
| 5 | `keyword_match` | 事業内容・サービス説明にターゲットキーワードが含まれるか判定 |
| 6 | `contact_form_find` | 問い合わせ・無料相談・見積もり・資料請求フォームURLを抽出 |
| 7 | `extraction_status` | 各項目が抽出できたか・未抽出かを記録 |
| 8 | `output_list` | Google Sheets / CSVに全件出力し、後工程でフィルタリング可能にする |

## ワークフロー

### Step 1: 入力読み込み

以下の入力を受け付ける:

- 既存の提案候補リスト（重複除外用）
- ポータルURL、検索結果、シード企業リスト
- ターゲット業種プロファイル名
- 包含キーワード
- 除外キーワード
- 出力形式（Google Sheets / CSV / JSON）

業種プロファイルが指定されない場合、ユーザーリクエストから最も近いプロファイルを推定し、仮定を明示する。

### Step 2: 除外インデックス構築

以下の **軽量フィルタファイル（`exclude_domains.txt`）** をローカルから読み込み、除外インデックスを構築する。

**ソースファイル:**
`scratch/company_search/exclude_domains.txt`
（約8,800件以上の既存ドメインが重複排除済みで保存されている）

**自動更新タイミング:**

```text
1. 起動時（Step 2）: `exclude_domains.txt` を読み込んでインデックスを構築（約0.1秒）
2. 出力後（Step 12完了後）: `sheets_writer.js` がGoogle Sheetsへの書き込み成功と同時に、新規企業のドメインを `exclude_domains.txt` に自動追記する
3. 次回起動時: 追記済みインデックスを読み込む（自動サイクル）
```

> [!IMPORTANT]
> スプレッドシート（Google Sheets API）へのアクセスは行わない。
> 完全ローカルのテキストファイル（ドメイン名のみ）を使用するため、数万件になってもO(1)検索で即座に判定可能。API制限によるエラーも発生しない。

**正規化キー:**

```text
normalized_domain        — 主キー（ドメイン一致で即判定）
normalized_company_name  — 補助キー（ドメイン不一致時の企業名照合）
```

**ドメイン正規化ルール:**

- 小文字化
- プロトコル除去
- `www.` 除去
- パス・クエリ文字列・フラグメント・末尾スラッシュ除去
- `/index.html` 等の明示的なインデックスページを正規化

例:
```text
https://www.example.co.jp/           → example.co.jp
http://example.co.jp/company/        → example.co.jp
https://example.co.jp/contact?ref=x  → example.co.jp
```

**企業名正規化ルール:**

- 法人格除去（株式会社、有限会社、合同会社、一般社団法人等）
- 全角→半角変換
- 大文字→小文字変換
- 空白除去

**除外インデックスの保存形式:**

```json
{
  "meta": {
    "lastUpdated": "2026-04-29T00:00:00.000Z",
    "totalCount": 9800,
    "version": "1.0.0"
  },
  "entries": [
    {
      "domain": "example.co.jp",
      "name": "株式会社サンプル",
      "normName": "さんぷる",
      "source": "Webマーケティング",
      "addedAt": "2026-04-29T..."
    }
  ]
}
```

> 対象企業は1万件近くに達している。JSONのMap/Set検索はO(1)であり、高速かつ確実に重複管理できる。

### Step 3: 候補収集（seed_collect）

ポータルサイト、カテゴリディレクトリ、比較記事、検索結果から候補企業を収集する。

**候補データ（軽量シードのみ）:**

```json
{
  "seed_source_url": "",
  "seed_source_name": "",
  "company_name": "",
  "listed_category": "",
  "candidate_official_url": ""
}
```

**ポータルサイトの利用ルール:**

- 企業候補の発見に使用する（Web幹事、比較サイト等）
- 業種カテゴリのヒントとして活用する
- 公式サイトURLの候補を得る
- **最終的な情報ソースにはしない**（代表者・資本金・従業員数等は公式サイトから取得）
- 利用規約上の制約がある場合、大量収集・二次利用に注意する

**事例記事の取り扱い:**

```text
✅ 許可: 業種ポータル（Web幹事等）からの企業候補収集
✅ 許可: 比較記事・カテゴリディレクトリからの候補収集
❌ 禁止: 成功事例・導入事例記事内の事例対象企業をノーチェックで取り込むこと
```

事例記事（マーケティング成功事例、導入事例等）に登場する企業は「事例提供側」であり、提案対象の文脈とは異なる。事例記事内企業を取り込む場合は、必ずキーワードHIT確認（Step 8）を経由すること。

**検索クエリ:**

`references/vertical-profiles.md` のキーワードを検索クエリとして使用する。

```text
基本形: "{キーワード} {地域} 会社"

例（Webマーケ系）:
  "SEO 東京 会社"
  "MEO対策 大阪 会社"
  "広告運用 名古屋 会社"

例（Web制作系）:
  "ホームページ制作 東京 会社"
  "WordPress制作 大阪 会社"
  "ECサイト構築 福岡 会社"
```

> [!NOTE]
> **マイナス検索の追加は補助的な最適化。** `-事例 -比較 -ランキング` 等を付けるとクロールコストを削減できるが、
> メインのフィルターは Step 8（キーワードHIT判定）であるため必須ではない。
> 「支援」等のワードは全ての対象企業に存在するとは限らないため、クエリに固定しない。

**除外ドメイン（適用タイミング）:**

→ `references/exclude-domains.md` 参照（60+ドメイン）

```text
適用タイミング:
  1. シード収集時: 候補URLのドメインを即照合。一致したら候補に入れない
  2. 公式サイト確定時（Step 4）: 確定URLのドメインを再照合。一致したら企業名で公式HP再検索

判定は「URLを発見した瞬間」に行う。後工程に持ち越さない。
```

### Step 4: 公式サイト確定（official_site_resolve）

候補企業の公式サイトを確定する。

**高信頼シグナル:**

- 企業名がページタイトル、ヘッダー、フッター、会社概要ページに表示
- 会社概要、問い合わせ、プライバシーポリシー、サービスページが存在
- 住所・代表者・電話番号がポータル情報と一致
- ドメインがマーケットプレイス、SNS、地図、求人、比較サイトではない

**ポータルサイト再検索:**

mynavi, doda, prtimes等のポータルドメインを検出した場合、企業名で公式HPを再検索する。

**不確定の場合:**

```text
official_url_status = uncertain
duplicate_status = unknown
```

不確定な公式サイトに抽出コストをかけない（ユーザーが積極的な補完を指示した場合を除く）。

### Step 5: 重複チェック（2段階）

公式サイトURLや企業名が判明した時点で、即座に除外インデックスと照合する。

**チェックタイミングと方法:**

| タイミング | チェック対象 | 判定 |
|-----------|-------------|------|
| 公式サイトURL取得時 | normalized_domain 一致 | → duplicate |
| 企業名取得時 | normalized_company_name 一致 | → duplicate候補 |

**重複ステータス:**

```text
duplicate_status:
  new          — 新規
  duplicate    — 重複確定
  suspected    — 重複疑い（企業名一致だがドメイン不一致）
  unknown      — 判定不能（公式URL未取得等）

duplicate_reason:
  domain_match
  name_match
  no_official_url
  none
```

**`suspected` の後続処理:**

```text
suspected（企業名一致・ドメイン不一致）が発生した場合:
  1. クロールは続行する（別法人の同名企業の可能性があるため）
  2. duplicate_status = suspected としてフラグを付ける
  3. 出力時に suspected 件数を品質レポートに含める
  4. 最終判断はリスト側で目視確認

例: 「株式会社サンプル」が example.co.jp（既存）と sample.co.jp（新規）の両方に存在
  → sample.co.jp 側を suspected として出力。同一企業かどうかはリスト側で判断
```

> [!IMPORTANT]
> 自動削除ではなく `duplicate_status` をフラグとして残す。最終判断はリスト側で行う。

### Step 6: 会社概要ページ探索（profile_page_find）

公式サイト内で会社概要ページを探索する。

**リンクテキスト:**

```text
会社概要
企業情報
会社案内
About
Company
Profile
Outline
```

**URLパス:**

```text
/company
/about
/profile
/outline
/corporate
/company-profile
/company/outline
```

テーブル、定義リスト、見出し付きの企業情報が含まれるページを優先する。
ブログ、ニュース、事例紹介、採用記事は初期抽出では追わない（サービスキーワード確認で必要な場合を除く）。

### Step 7: 企業情報抽出（company_fields_extract）

テキストとして抽出し、必要に応じて数値を正規化する。

**抽出フィールド:**

```json
{
  "company_name": "",
  "representative_name": "",
  "capital_text": "",
  "capital_amount_jpy": null,
  "employee_text": "",
  "employee_count": null,
  "address": "",
  "business_description": "",
  "service_description": "",
  "source_urls": []
}
```

**抽出ソース（優先順）:**

1. HTMLテーブル（th/td構造）
2. 定義リスト（dl/dt/dd構造）
3. 会社概要セクション
4. フッターの企業情報ブロック
5. Aboutページ
6. サービス概要ページ

**抽出パターンの詳細:**

→ `references/extraction-patterns.md` 参照（企業名5段階・従業員数12パターン・代表者名11パターン・資本金3パターン）

**バリデーションルール:**

→ `references/validation-rules.md` 参照

確定的な抽出（DOM解析・正規表現）を先に行う。AIは曖昧・断片的なテキストの場合のみ使用する。

**従業員数・資本金の補完ソース:**

```text
公式サイトのみを情報源とする。外部ソース（求人サイト・Wantedly・登記情報等）は使用しない。

理由:
  - 外部ソースは更新が遅く、実態と乖離することがある
  - ソースの一次情報として公式サイトが最も信頼性が高い
  - 取得できない場合は not_found ステータスで記録し、推測・補完しない
```

**大企業シグナル即除外（クロール中に検出した場合、以降の工程をスキップして即除外）:**

```text
【テキスト内に含まれるキーワード — 即除外】
  上場キーワード（14個）: 東証プライム、東証スタンダード、東証グロース、
                         東証一部、東証二部、JASDAQ、マザーズ、上場企業、
                         証券コード、株式上場、IPO、東京証券取引所、
                         名古屋証券取引所、札幌証券取引所、福岡証券取引所
  大企業向け         — サービス対象が大企業と明示
  グループ会社       — 大企業グループ傘下の可能性
  従業員100名以上    — 規模閾値超過
  上場準備中         — 近い将来に上場予定

【サイト内にページ/リンクが存在する場合 — 即除外】
  組織図             — 小規模企業に組織図ページは稀。大企業シグナル

【記録のみ・即除外しない】
  沿革               — 中小企業にも一般的なページ。大企業シグナルとして弱い
                       → notes フィールドに「沿革ページあり」と記録し、リスト側で判断

【除外しない】
  全国               — 「全国対応」等、対象企業にも含まれることがある
```

### Step 8: キーワード判定（keyword_match）★ポジティブフィルター

公式サイトのサービス関連ページにターゲットキーワードが含まれるかを判定する。

**判定対象ページ（優先順）:**

```text
1. サービスページ（/service, /services, サービス, 事業内容）
2. トップページ（/）
3. 会社概要ページ（/company, /about, 会社概要）
```

**判定対象テキスト:**

ページの `<body>` 内テキストから `<nav>`, `<header>`, `<footer>`, `<aside>` を除外したメインコンテンツ領域。
ブログ・事例記事・採用ページのテキストは含めない（顧客企業のキーワードによる誤判定防止）。

**判定フロー:**

```text
1. 上記ページのメインコンテンツにキーワードが1つでも存在するか確認
2. 存在する → keyword_status = matched → 候補本体に残す
3. 存在しない → keyword_status = not_matched → 候補本体から除外し、別出力（unmatched）に退避
4. クロールできなかった → keyword_status = unknown → 候補本体に残す（要手動確認フラグ）
```

**`not_matched` 企業の扱い:**

自動削除ではなく、`unmatched_candidates` として別出力する。後から目視で確認・復帰可能にする。

**保存フィールド:**

```json
{
  "matched_keywords": [],
  "negative_keywords": [],
  "keyword_status": "matched | not_matched | unknown"
}
```

**negative_keywords の用途:**

```text
企業サイトに含まれていたら「提案対象外の可能性あり」を示すワード。
即除外はしない。「除外根拠候補」として記録し、リスト側でフィルタリングする。

記録対象の例:
  大企業向け、上場企業向け、グループ会社、全国拠点、
  フランチャイズ、従業員100名以上、上場準備中

※ 東証プライム・上場企業 等の上場キーワード14個は
  negative_keywords への記録ではなく CHECK-D で即除外する（別処理）。
```

> [!IMPORTANT]
> `matched_keywords` は「この企業が対象である根拠候補」として保存する。
> ワード判定だけで業種を確定すると雑になる。根拠候補として保存し、リスト側で精査する。

**キーワードプロファイル:**

→ `references/vertical-profiles.md` 参照

### Step 9: 問い合わせフォームURL抽出（contact_form_find）

問い合わせ・相談・見積もり・資料請求のフォームページを探索する。

**リンクテキスト:**

```text
お問い合わせ
お問合せ
無料相談
相談する
見積もり
お見積り
資料請求
CONTACT
Contact
Inquiry
Request
```

**URLパス:**

```text
/contact
/inquiry
/form
/estimate
/request
/consultation
```

**フォームURLのステータス:**

```text
contact_status:
  found       — フォーム発見
  not_found   — フォームなし
  uncertain   — 不確定
  ng          — 営業NG文言あり
```

**フォームの扱い:**

フォームURLがない企業は提案対象としての優先度が低い。
ただし自動削除はせず、`contact_status = not_found` のフラグを付けてリストに残す。

```text
デフォルト動作:
  フォームなし → contact_status = not_found → リストに残す（優先度低フラグ）
  フォームあり → contact_status = found → リストに残す
  営業NG → contact_status = ng → リストに残す（NG理由付き）

出力後のフィルタリング:
  リスト側で contact_status = found のみに絞り込むことで、フォームあり企業だけを対象にできる
```

> [!NOTE]
> フォームなし=即除外ではない。電話番号やメールアドレスで連絡可能な企業もある。
> フィルタリングはリスト側の判断に委ねる。

**営業NG文言チェック:**

フォームページに営業拒否文言がある場合、NG理由を記録する。
ただし以下は誤検知として除外する:

```text
誤検知パターン（NGにしてはいけない）:
- 安心訴求: 「営業電話することはありません」（自社がしない宣言）
- 職種名: 「印刷媒体・WEB媒体／営業・制作」
- 自社サービス説明: 「弊社営業より提供のご案内」
- コンテンツ文章: 「営業と兼任でマーケティングを担当」
- 法的表明: 「金融商品取引法に基づく勧誘」
```

フォーム送信はこのスキルでは行わない。

### Step 10: 品質ゲート（工程内バリデーション）

出力前に全レコードに対して品質チェックを実施する。通過しないレコードは出力しない（またはフラグ付き）。

**CHECK-A: 企業名バリデーション**

→ `references/validation-rules.md` の企業名ルール適用
- 人名パターン（漢字姓+スペース+漢字名）→ 除外
- ラベル語完全一致（企業情報、会社名、経歴等）→ 除外
- 役職切れ端+人名（長 伊藤、社長 田中）→ 除外
- 執筆者情報（〜執筆の、〜監修）→ 除外
- 法人格のみ・法人格+敬称 → 除外
- 文章片（助詞含有・ひらがな末尾）→ 除外

**CHECK-B: 代表者名バリデーション**

1. `cleanRepresentativeName`: ゴミ除去（役職/敬称/一般名詞）
2. `isJapanesePersonName`: 正判定（漢字姓名/スペース区切り）
3. 不合格 → 「ご担当者」にフォールバック

**CHECK-C: URL-企業名整合性**

公式サイトの `<title>` または `<footer>` に企業名が含まれるか確認。
含まれない場合、提携先・事例の誤抽出の可能性が高い。

```text
照合ルール:
  1. 法人格を除去した企業名コア部分で照合する
     例: 「株式会社サンプル」→ 照合キー「サンプル」
  2. 全角/半角・大文字/小文字を正規化してから照合
  3. 部分一致で判定（titleの一部に含まれればOK）
     例: title「サンプル｜Web制作会社」→ ✅ 含まれる
  4. 企業名の表記ゆれを考慮
     例: 「SAMPLE」と「サンプル」は別表記として不一致扱い

判定結果:
  含まれる → OK（公式サイトとして信頼）
  含まれない → url_name_mismatch フラグを付けて出力（自動削除しない）
  title/footer取得不可 → unknown
```

> [!NOTE]
> 自動除外ではなくフラグ方式にする理由: 英語表記のみのサイト（title: "SAMPLE Inc."）で
> 日本語企業名「サンプル」が見つからないケースがある。誤除外を防ぐため目視確認に回す。

**CHECK-D: 上場企業・大手判定**

→ `references/validation-rules.md` の上場キーワード14個で判定。検出時は絶対除外。

**CHECK-E: 資本金バリデーション**

- 数字 + 万円/億円/円 → 合格
- 円表記なしの純数字6桁以上 → `{数字}円` として採用
- 文章片・JSON断片・メールアドレス等 → 空にリセット

**CHECK-F: 間借りドメイン判定**

`hp.xxx.co.jp` 等のサブドメイン借用 → 除外。

**CHECK-G: 品質統計出力**

全項目の統計と残存問題数を出力し、品質チェック完了を明示する。

## AI利用方針

AIはスクレイピング・DOM解析・正規表現で取れないギャップにのみ使用する:

- 公式サイト候補が複数あり判定が難しい場合
- 会社概要の表記が崩れている場合
- 従業員数・資本金の表記が文章中に埋もれている場合
- 事業内容やサービス内容の分類に判断が必要な場合

ページ全文をAIに渡さない。会社概要周辺・サービス説明周辺など、短いテキストに切り出してから渡す。
これによりトークン消費を抑制し、再現性を高める。

## デフォルト設定

```text
重複判定の主キー:
  normalized_domain

抽出方針:
  抽出してステータスを付ける（早期除外しない）

フィルタリング方針:
  重複以外は自動削除しない（ステータスで判定を残す）

政府系レジストリ:
  ユーザーが明示的に指示しない限りスキップ
  （国税庁法人番号・Gビズインフォ・EDINET等）
```

小規模企業では公式サイトの方が政府系レジストリより実務的な情報源になる。
目的は法的な法人確認ではなく、提案候補の発見と構造化である。

## 品質基準

出力前に必ず確認する:

- 重複行がドメイン・企業名で検出・フラグ付けされている
- 公式サイトURLがポータル・SNS・求人・比較サイトではない
- 問い合わせフォームURLが実際の企業ページである
- 重要な値にはソースURLが付いている
- 未取得データはステータスフィールドで表現されている（空欄で放置しない）
- キーワードHIT未確認の企業が候補本体に混入していない
- 上場企業が候補に残っていない
