# プロ事例の証拠条件

## 目的

プロ事例、成功事例、うまくいっている事例を、出典なしの思いつきと混ぜない。
作業前に「確認済み」「未確認」「使わない」を分ける。

## プロ事例と呼んでよい条件

次の条件をすべて満たすものだけを、プロ事例として扱う。

| 条件 | 合格 | 不合格 |
|:---|:---|:---|
| 出典 | URLまたはローカルパスがある | 出典名だけ、記憶だけ |
| 確認日 | いつ確認したかが分かる | 古い記憶だけ |
| 実物 | 実本文、実プロンプト、実AGENTS.md、実スキル、実行ログのどれかを読んでいる | 要約、紹介文、感想だけ |
| 成功根拠 | 数字、公開実績、採用状況、運用実績、実ファイルで確認できる | 「良さそう」「有名だから」だけ |
| 採用点 | 今回使う作業ルールが明確 | 何を真似るか不明 |
| 不採用点 | そのまま真似しない点が明確 | 文面や構造を丸ごと移す |
| 中身の型 | 同じ種類の成果物から、見出し、文量、命令の粒度、例の置き方、検証方法、失敗時の扱いを確認している | 大枠の説明だけ、形式紹介だけ |

## 出典の種類を分ける

| 種類 | 使い道 | 注意 |
|:---|:---|:---|
| 公式仕様 | 守るべき制約、用語、ファイル形式を決める | これだけで成功事例とは呼ばない |
| 成功事例 | 実際にうまくいった運用の型を採用する | 数字、採用状況、実ファイルなどの根拠を見る |
| 実ファイル | 書き方、分量、構造を確認する | そのrepo固有の手順をそのまま移さない |
| 評価事例 | テスト方法、比較方法、判定方法を採用する | 評価条件が今回にも合うか確認する |
| 失敗例・反証 | やってはいけない形を確認する | 失敗理由が今回にも当てはまるか確認する |

## 中身の型として確認すること

プロンプト、スキル、`AGENTS.md`、プラン、設計方針、A/B計画、レビュー判断、運用ルール、評価ケースを作る場合は、同じ種類の実物から次を確認する。
この表が空のままなら、本文を書き始めてはならない。

| 観点 | 確認すること |
|:---|:---|
| 見出し構成 | どの見出しが、どの順番で置かれているか |
| 文量 | 入口は短いか、詳細は別ファイルか、本文はどの程度の密度か |
| 命令の粒度 | 義務、任意、停止条件、例外が分かれているか |
| 例の置き方 | 自作例、実例、テンプレート、入力出力例が混同されていないか |
| 検証方法 | 発火テスト、出力テスト、比較、再実行条件があるか |
| 失敗時の扱い | 未確認、停止、再確認、ロールバックのどれを使うか |
| 真似しない点 | そのrepo固有のコマンド、英語表現、不要な重さを持ち込まないか |

## 証拠表の形式

作業前または作業案の中で、次の形に整理する。

| ID | 種類 | 出典 | 確認日 | 実物として読んだ範囲 | 確認できたこと | 採用する点 | 採用しない点 |
|:---|:---|:---|:---|:---|:---|:---|:---|

|:---|:---|:---|:---|:---|:---|:---|:---|:---|

## 採用判断

- 採用するのは、文面ではなく作業ルールにする。
- 公式資料は仕様根拠として使えるが、それだけで成功事例とは呼ばない。
- 公開事例は、本文や実ファイルを読める範囲だけを使う。
- 英語の実例を使う場合も、成果物は日本語Markdownに置き換える。
- 成功根拠が弱い場合は、参考情報として扱い、プロ事例とは呼ばない。
- ユーザーが「徹底的に」と求めた場合は、公式仕様、成功事例、評価方法、反証または失敗例を分けて確認する。
- ユーザーが「中身の書き方」を求めた場合は、同種成果物の実物を読み、上の `中身の型` を必ず埋める。
- 出典が不足している場合は、確認済み扱いにせず `未確認で停止` とする。

## 不合格時の対応

- 実本文がない場合は、未確認材料へ戻す。
- 採用点と不採用点が分かれていない場合は、証拠表を作り直す。
- 出典が公式資料だけの場合は、仕様根拠と実運用事例を分ける。
- 大枠だけで中身の型がない場合は、同種成果物の実物を追加で確認する。
- 使える事例が見つからない場合は、プロ事例確認済みと言わず、出力の型だけを示す。
- 作業前チェックメモの必須欄が埋まらない場合は、作業へ進まない。
