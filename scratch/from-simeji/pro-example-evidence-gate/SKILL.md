# プロ事例証拠ゲート

プロ事例の実物、出典、採用理由、中身の型を確認し、作成・修正・評価へ進めるかを判定する。
中身の型は、同種成果物の見出し、文量、命令の粒度、例の置き方、検証方法、失敗時の扱いを指す。
作業前チェックメモは、憶測で本文を書かないための確認跡として作る。
必要な検索、ファイル確認、コマンド確認は必ず自動実行する。
停止する場合も、必ず [references/check-memo-format.md](references/check-memo-format.md) の見出し順で作業前チェックメモを出す。

## ステップ1: 対象と調査レベルを決める

- [ ] 何を作る、直す、評価する依頼かを1文で書いた。
- [ ] 成果物の種類を決めた。例: `SKILL.md`、`AGENTS.md`、プロンプト、プラン、設計方針、A/B計画、評価ケース、運用ルール。
- [ ] 調査レベルを `軽量`、`標準`、`徹底` のどれかで決めた。
- [ ] 見る同種成果物の実物を決めた。
- [ ] Codex、AGENTS.md、スキル、プロンプト、品質改善に関係する場合は、[references/confirmed-codex-sources.md](references/confirmed-codex-sources.md) を必ず読む。

#### 入力

ユーザー依頼、対象ファイル、作業目的。

#### 出力

対象範囲、調査レベル、確認すべき同種成果物。

#### 完了条件

対象範囲、調査レベル、見る材料、見なくてよい材料が明確であること。この完了条件を満たすまで次に進んではならない。

## ステップ2: 実物の証拠と中身の型を集める

- [ ] [references/evidence-requirements.md](references/evidence-requirements.md) を必ず読む。
- [ ] 公式仕様、成功事例、実ファイル、評価事例、失敗例を混ぜずに分けた。
- [ ] 出典URLまたはローカルパスだけでなく、確認日、実際に読んだ範囲、成功根拠を確認した。
- [ ] 同じ種類の成果物を最低1つ読み、見出し、文量、命令の粒度、例の置き方、検証方法、失敗時の扱いを記録した。
- [ ] 大枠のベストプラクティスだけで、本文の書き方まで確認した扱いにしていない。
- [ ] 証拠が足りない材料を、未確認材料へ分けた。

#### 入力

調査対象、検索結果、公式資料、実ファイル。

#### 出力

プロ事例証拠表、中身の型、未確認材料表。

#### 完了条件

確認済み材料、中身の型、未確認材料、使わない材料が分かれていること。この完了条件を満たすまで次に進んではならない。

## ステップ3: 採用する点と採用しない点を分ける

- [ ] 各プロ事例について、今回採用する作業ルールを1つ以上書いた。
- [ ] 各プロ事例について、今回そのまま真似しない点を書いた。
- [ ] 文面を丸写しせず、見出し構成、具体性、検証方法などの使える型へ変換した。
- [ ] 成功根拠がない材料を、採用根拠に入れていない。
- [ ] 出力の型に迷う場合は、[examples/check-memo-cases.md](examples/check-memo-cases.md) を読む。

#### 入力

証拠表、中身の型、未確認材料、ユーザー目的。

#### 出力

採用ルール、採用しない点、未確認のまま残す点。

#### 完了条件

採用する点、採用しない点、中身の型の反映方法が分かれていること。この完了条件を満たすまで次に進んではならない。

## ステップ4: 作業前チェックメモを出す

- [ ] [references/check-memo-format.md](references/check-memo-format.md) を必ず読む。
- [ ] 作業前チェックメモを日本語Markdownで作成した。
- [ ] 作成・修正・評価へ進んでよいかを `進行可` または `未確認で停止` で判定した。
- [ ] `中身の型` の見出しを省略していない。
- [ ] `未確認で停止` の場合、足りない証拠と次の確認先を書いた。
- [ ] 指定された見出し順、必須欄、停止条件を省略していない。

#### 入力

証拠表、中身の型、未確認材料、採用ルール。

#### 出力

作業前チェックメモと進行判定。

#### 完了条件

作業前チェックメモに、判定、対象、確認済み材料、中身の型、採用すること、採用しないこと、未確認材料、次の作業が含まれること。確認済み材料には出典、確認日、実際に読んだ範囲があること。この完了条件を満たすまで次に進んではならない。

## ステップ5: 自己完了確認を行う

- [ ] 出典URLまたはローカルパスがある。
- [ ] 確認日がある。
- [ ] 実本文、実プロンプト本文、実AGENTS.md、実スキル本文、または実行ログを読んでいる。
- [ ] 同種成果物の中身の型を確認している。
- [ ] 成功根拠がある。
- [ ] 採用する点と採用しない点が分かれている。
- [ ] 未確認材料を確認済みとして扱っていない。
- [ ] 上記が1つでも欠ける場合は、完了報告せず `未確認で停止` として報告した。

#### 入力

作業結果、証拠表、中身の型、未確認材料。

#### 出力

完了可否と、ユーザーへ出す確認済み/未確認の報告。

#### 完了条件

全チェックが完了していること。未実施のステップがある場合は完了報告してはならない。

## エッジケース

| 状況 | 対応 |
|:---|:---|
| URLだけ見つかり、本文を読めない | プロ事例ではなく未確認材料にする |
| 公式資料はあるが成功事例ではない | 仕様根拠として扱い、うまくいっている事例とは分ける |
| 大枠のベストプラクティスしかない | 中身の型は未確認として止めるか、同種成果物を追加で読む |
| 同種成果物が見つからない | 近い成果物を使う理由と限界を書き、未確認材料にも残す |
| スキルが発火しない恐れがある | `AGENTS.md` に短い入口ルールを置き、descriptionに発火条件を置く |
| 事例の形式が英語またはタグ形式 | 意味だけ採用し、日本語Markdownへ置き換える |
| 出力が毎回揺れる | 固定テンプレート、必須欄、検証ループを置く |
| 検証で落ちた | 原因を直して同じ確認を再実行し、通るまで完了扱いにしない |

## 禁止事項

- 出典や実本文を確認していない材料を、プロ事例として扱ってはならない。
- 大枠の手順だけを見て、中身の書き方まで確認したと言ってはならない。
- 自分で作った例を、成功事例、実例、良い例として置いてはならない。
- 公式資料だけを見て、うまくいっている実運用事例まで確認済みと言ってはならない。
- URLだけ、要約だけ、印象だけで完了扱いにしてはならない。
- 英語のプロ事例をそのまま貼るだけで、日本語Markdownへ置き換える工程を省略してはならない。
- 作業前チェックメモの必須見出しを省略してはならない。
- 停止時に、通常の進捗報告だけで終えてはならない。
