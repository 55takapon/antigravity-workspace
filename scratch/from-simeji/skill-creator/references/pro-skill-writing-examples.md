# プロ品質の粒度見本

この資料は、複雑なスキル、文章生成スキル、プロンプト生成スキル、生データやプロ事例が必要なスキルで読む。
目的は「どのくらい具体的に書けば、実際に作業できるか」をそろえること。

単純な確認手順だけのスキルでは読まない。

---

## 根拠メモ

ここにあるパスや固有名は、この資料を作る時に確認した根拠です。
新しく作るスキルの本文へ、固定パスとして書き込まない。

| 種類 | 確認した実物 | 採用する点 |
|:---|:---|:---|
| 公式 | OpenAI skill-creator | `SKILL.md` と `references/` の重複を避け、必要な資料だけ読む |
| 公式 | Agent Skills best practices | 実務知識、実行結果、レビュー結果から改善する |
| 公式 | Agent Skills evaluating skills | 実入力、期待出力、実行結果を見て改善する |
| ローカル実例 | `x-post-builder-prompted` | `SKILL.md` は工程リンク中心、詳しいプロンプトは `references/` |
| ローカル実例 | `discord-post-builder` | 実素材、本人実例、別担当確認、禁止事項、自己確認を分ける |

採用しないもの:

- 固定パスを新規スキルの標準手順として書くこと。
- 実物を見ていないものをプロ事例として扱うこと。
- 作り物の完成文を良い例として置くこと。
- プロ事例がタグ形式だからという理由だけで、タグ形式をそのまま移すこと。
- 検証者がやるA/B作業を、作成されるスキル本文へ混ぜること。

## 浅い書き方とプロ品質の違い

### 浅い書き方

```markdown
## ステップ1: 材料確認

- 材料を確認する
- 足りないものを質問する
- 次に進む
```

問題:

- 何を材料として扱うか分からない。
- 何を見て足りないと判断するか分からない。
- 次工程へ何を渡すか分からない。
- 出典のないプロ事例や作り物の例が混ざっても止まらない。

### プロ品質の書き方

```markdown
## ステップ1: 材料を確認する

必要資料: [references/01_材料確認.md](references/01_材料確認.md) をこの工程で必ず読む。

- [ ] ユーザー提供例、実ファイル、公開されているプロ事例、未確認材料を分けた
- [ ] プロ事例は、出典だけでなく実本文または実プロンプト本文を確認した
- [ ] 次工程で使う材料と、使わない材料を理由付きで分けた

#### 完了条件
- 次工程へ渡す材料カードができていること
- 未確認材料が、本文用の材料へ混ざっていないこと
- 材料不足なら本文作成へ進まず、質問すること
```

良い点:

- 何を見るかが分かる。
- 何を次へ渡すかが分かる。
- 材料不足時の対応が分かる。
- 詳細は `references/` へ分かれているため、`SKILL.md` が重くならない。

## SKILL.md に書く粒度

`SKILL.md` は入口です。
毎回読む必要がある内容だけを置く。

書くもの:

- スキルの目的
- 発火条件を含む description
- 実行手順
- 各工程で読む資料
- エッジケース
- 禁止事項
- 自己完了確認

書かないもの:

- 長い品質基準
- 詳しい判定表
- 実例本文の束
- 工程別プロンプト本文
- A/B検証者の作業メモ

---

## references に書く粒度

`references/` は、工程で必要になった時だけ読む詳細資料です。
複雑な工程は、番号付きファイルに分ける。

工程別 references に入れるもの:

- 目的
- 使う材料
- 見る観点
- 作業手順
- 出力形式
- 確認方法
- 不合格時の対応

浅い例:

```markdown
## 作業手順

1. 材料を見る
2. 構成する
3. 確認する
```

プロ品質の例:

```markdown
## 作業手順

1. 確認済み材料だけを、出典付きで並べる。
2. 使わない材料を、理由付きで分ける。
3. 未確認材料を本文材料へ混ぜず、質問候補にする。
4. 次工程へ渡す材料カードを作る。
5. 材料カードに出典がない行があれば、次工程へ進まない。
```

---

## examples に書く粒度

`examples/` は、実際の入力と出力、または出力の型を置く場所です。
工程の説明や判断基準は置かない。

実データがある場合:

```markdown
## 入力

- 実際の依頼文
- ユーザー提供素材
- 制約

## 出力

- 実際に合格した出力
- 出力後の確認結果
```

実データがない場合:

```markdown
## 入力

- 材料:
- 目的:
- 制約:

## 出力

- 完成物:
- 使った材料:
- 未確認のため入れなかった内容:
- 確認結果:
```

これは空欄のまま完成例として置くためではない。
実行時に必要な入力と、完成後に確認する項目を見せるための型。

## プロンプト成果物の粒度

プロンプトを成果物として作る場合は、説明ではなく、そのまま実行できる本文にする。

浅い例:

```markdown
良い感じに記事構成を作ってください。
```

プロ品質の例:

```markdown
# 構成作成プロンプト

## 何をするか

材料カードを使って、記事の構成案を作る。
実素材にない話は入れない。

## 入力として受け取るもの

- 材料カード
- 想定読者
- 記事の目的
- 使わない材料

## 作業手順

1. 材料カードから中心の主張を1つ選ぶ。
2. 読者が読む前に困っていることを1文で書く。
3. 見出しを3〜5個作り、各見出しに対応する実素材IDを付ける。
4. 実素材IDが付かない見出しは削る。
5. 使わない材料にある数字、成果、体験談、断定が混ざっていないか確認する。

## 出力形式

| 見出し | 役割 | 使う実素材ID |
|:---|:---|:---|

## 確認結果

- 実素材にない話:
- 未確認のまま残した話:
- 削った内容:

## 不合格時の対応

- 実素材IDがない見出しは削る。
- 未確認材料を根拠にしている場合は、構成案へ入れず質問候補へ戻す。
- 読者と中心の主張がずれている場合は、想定読者から作り直す。
```

この例は、完成記事ではなくプロンプト本文の粒度見本です。
実行時には、実際の材料カードと制約を受け取って使う。

---

## 最後に確認すること

- `SKILL.md` に長い判定表や実例本文を入れていない。
- 必要な `references/` を、該当工程の中で読む形にしている。
- 実例や出力の型は `examples/` に分けている。
- 生データや長い原文は `knowledge/` または `examples/` に分けている。
- プロ事例は実物確認済みで、採用する点と採用しない点が分かれている。
- 作り物の完成文を、良い例として置いていない。
