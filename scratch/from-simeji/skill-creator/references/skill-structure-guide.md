# スキル構造設計ガイド

スキルのファイル構造を設計する際に参照するガイド。

---

## 公式推奨構造

OpenAI Codex の skill-creator ガイドに沿い、SKILL.md は概要とナビゲーションに絞り、詳細資料は必要時だけ読む。

```
my-skill/
├── SKILL.md (required - overview and navigation)
├── references/ (detailed rules - loaded when needed)
├── examples/ (usage examples - loaded when needed)
└── scripts/ (utility scripts - executed, not loaded)
```

SKILL.md内での参照方法:
```markdown
## ステップ1: データ取得

必要資料: API仕様が必要な場合だけ [references/api-spec.md](references/api-spec.md) をこの工程で読む。

- [ ] データを取得した

## ステップ3: 報告作成

必要資料: 出力形式に迷う場合だけ [examples/good-output.md](examples/good-output.md) をこの工程で読む。
```

## Progressive Disclosure（段階的開示）3層モデル

| 層 | いつ読まれるか | 何を置くか |
|:--|:------------|:---------|
| Layer 1: メタデータ | スキル発見時（常に） | name + description（YAML frontmatter） |
| Layer 2: SKILL.md本文 | スキル起動時 | 概要、必要資料を各工程内に含めた手順アウトライン、エッジケース、禁止事項、自己完了確認 |
| Layer 3: 分離ファイル | 実行中に必要時のみ | 詳細ルール、判定基準、工程別の詳しい手順、粒度見本、実例、生データ、出力の型 |

---

## 分離判定フロー

以下の順番で「何をSKILL.mdに書き、何を分離するか」を判定する:

1. すべての実行で必ず読む入口、手順、読む資料、エッジケース、禁止事項、自己完了確認か? → **はい** → SKILL.md に置く
2. 判定基準、表記ルール、品質基準、ツール仕様、プロ事例の分析、工程別の詳しい作業内容か? → **はい** → references/ に分離
3. 複雑な作業で工程ごとの詳しい指示があるか? → **はい** → `references/01_依頼整理.md` のように番号付きで分離
4. 工程の中で使う入力カード、確認表、作業パックなどの詳しい型か? → **はい** → その工程の references/ に置く
5. 実際の入力→出力の例、完成後にどの形になるかを見せる出力の型か? → **はい** → examples/ に置く
6. 長い原文、生データ、ユーザー提供素材、全文の実例か? → **はい** → knowledge/ または examples/ に置く
7. 上記全てなし + SKILL.md 80行以下 → references/ は省略可（examples/ は必須）

`prompt-index.md` と `prompt-quality-requirements.md` は標準では作らない。
必要になった場合も、なぜ通常の番号付き references では足りないのかを先に確認する。

## 会話から入れる内容の選び方

チャット内容には、スキルへ入れるべき作業ルールと、今回だけの作業者向け注意が混ざる。
SKILL.mdへ入れる前に、次のように分ける:

| 種類 | 扱い |
|:---|:---|
| 別の依頼でも使う手順 | SKILL.md の手順に入れる |
| エッジケース、禁止事項、自己完了確認 | SKILL.md に入れる |
| 判断基準、表記ルール、品質基準 | references/ に入れる |
| 工程ごとの詳しい作業手順 | references/ に入れる |
| 入力→出力の実例 | examples/ に入れる |
| 完成形を見せる出力の型 | examples/ に入れる |
| 工程の途中で使う入力カードや確認表 | その工程の references/ に入れる |
| ユーザー提供の生データ | examples/ または knowledge/ に入れる |
| 今回だけの注意、感情的な表現、叱責 | そのまま入れない。再利用できる作業ルールに直せる場合だけ入れる |
| 比較検証の手順や検証者の作業メモ | スキル本文に入れない。検証レポート側に残す |

見出しは、一読して意味が分かる言葉にする。
短すぎて意味が伝わらない見出しや、作業者だけが分かるラベルは使わない。
成果物、停止条件、差し戻し先などを短く切っただけの独自ラベルや、自然さを固定するような不自然な言い回しは使わない。

## 材料確認の進め方

スキルを作る前に、次の材料があるかを分ける。

| 材料 | 扱い |
|:---|:---|
| ユーザー提供例 | 実例として使う。必要なら examples/ または knowledge/ に置く |
| 生データ | 抜粋で代用せず、スキルが直接読める場所に置く |
| 公式資料 | 仕様やプロンプト品質の根拠として使う |
| 公開されているプロ事例 | 検索して実物を確認できた場合だけ使う |
| ローカル実ファイル | ユーザー指定または今回の作業に直接関係する場合だけ使う |
| 未確認の材料 | 確認済みとして扱わず、質問または未確認にする |

プロ事例を探す必要がある場合は、検索、公式資料、ユーザー提供例、ローカル実ファイルの順に実物を確認する。
固定のローカルスキル名や固定パスを、ユーザー指定なしにプロ事例として扱わない。

## プロンプト成果物の書き方

プロンプト、テンプレート、文章作成手順を成果物にする場合は、Markdown文書として自然に読める形で書く。
標準では山括弧で役割や出力形式を囲むタグ形式、JSON、YAMLだけの形式にしない。
プロ事例や別スキルの実例がタグ形式でも、その構造は引き継がず、Markdown見出しへ置き換える。
三点リーダー、未定稿表記、穴埋め指示のような未完成の文は残さない。
材料不足で本文を埋められない場合は、完成例を作らず、必要な材料を質問するか、コピー用ではない出力の型として明記する。

### 標準のMarkdown構成

工程別プロンプトは、必要に応じて次の見出しで書く。

- 何をするか
- 使う材料
- 見る観点
- 作業手順
- 出力形式
- 確認方法
- 不合格時の対応

各見出しには実際に使える指示文を書く。
見出しだけ置いて中身を省略してはならない。

### 使わない標準形式

山括弧で役割や出力形式を囲むタグ形式は標準では使わない。
禁止例としても、実際のタグ本文を置かない。
ユーザーが今回の成果物でタグ形式を明示した場合だけ使う。

タグ形式を使う場合は、なぜMarkdown見出しでは足りないのかを明記する。

## 具体例の材料

具体例は、実際の入力と出力の対を置く。
文章、投稿、文体、マーケティング系では、作成者が想像した完成文を良い例として置かない。
実データがない場合は、コピーできる完成文ではなく、入力項目や出力の型だけを示す。

`プロ事例` と呼ぶファイルには、参照元名、出典パスまたはURL、実本文または実際のプロンプト本文を入れる。
出典と本文がない抽象メモは、プロ事例ではなく references/ の型や確認基準として置く。

## 良い例 / 悪い例

### 良い例: strict-impact-analysis

```
strict-impact-analysis/
├── SKILL.md (67行, 656トークン)
└── scripts/
    └── find_dependencies.py
```

SKILL.md本体: 手順アウトライン + 入出力 + 完了条件のみ。
スクリプトに確定的処理を委譲。

### 悪い例: pro-planner（修正前）

```
pro-planner/
└── SKILL.md (248行, 3,000トークン)
```

SKILL.md本体に全て詰め込み:
- 監査ループの詳細手順
- テーブル例
- 禁止事項の詳細説明
- → 推論低下閾値（3,000トークン）に到達

### 改善例: pro-planner（あるべき姿）

```
pro-planner/
├── SKILL.md (80行, ~1,500トークン)
├── references/
│   └── audit-process.md (監査詳細)
└── examples/
    └── good-output.md (プラン例)
```
