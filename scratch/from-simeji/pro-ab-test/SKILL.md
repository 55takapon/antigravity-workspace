# Pro AB Test

スキル、プロンプト、生成文の改善を、思いつきの修正ではなく「変更前後の実物比較」で判断する。改善作業は、編集前のA/B設計からすでに始まっているものとして扱う。

必要なツールを使って即座に自動実行すること。ユーザーへの確認は不要。

## 必須実行ルール

- 重要資料は、該当工程に入った時点で必ず読む。読んでいない工程は完了扱いにしない。
- すべての資料を最初にまとめ読みしない。工程に必要な資料だけを読み、判断に使う。
- A/B開始前に、何を良くするか、何を比べるか、どう測るか、どこから勝ちか、何が悪化なら戻すかを固定する。
- 1回のA/Bで変える点は1つだけにする。複数の原因を同時に変えた場合、そのA/Bは無効にする。
- A案とB案は、同じ入力、同じルート、同じ判定基準で比べる。
- スキル改善のA/Bは、対象エージェントが実際の利用時と同じ入口から自立してスキルを使った出力だけを有効にする。依頼者や検証者が工程ごとの修正指示、文体指示、差し戻し文を手で足して作らせた出力は無効にする。
- 対象スキルを使った証拠として、実行ログにスキル入口、必要工程、実例参照、品質判定が残っていない場合は無効にする。本文の良し悪しを判定する前に、まず実行ルートを無効にする。
- 実本文または実成果物を横並びで見ない限り、改善したと報告しない。
- 残す/戻す/無効のどれかを必ず決める。根拠が弱い変更は残さない。

進捗チェックリスト:

- [ ] A/B開始条件を固定した
- [ ] プロ事例に沿って計画した
- [ ] 変更前のA案を実ルートで出した
- [ ] 1点だけ変更してB案を出した
- [ ] 対象エージェントが自立して対象スキルを使った実行ログがある
- [ ] 実物を横並びで判定した
- [ ] レビュー担当を使う場合は材料を揃えた
- [ ] 残す/戻す/無効を完了した

## 手順アウトライン

1. **A/B開始条件を固定する**: 改善対象、ユーザー目的、変更前の状態、比較に使う実入力、測定基準、合格ラインを必ず特定すること。
   必須資料: [references/experiment-protocol.md](references/experiment-protocol.md)、[references/measurement-rubric.md](references/measurement-rubric.md) をこの工程に入ったら必ず読む。
   入力: ユーザー依頼、対象ファイル、変更前のファイル差分、変更前の実出力、実入力、既知の失敗例、ユーザー指定の実例や生データ。
   出力: A/B開始メモ。目的、A案、入力、変更点、仮説、主判定、測り方、合格ライン、補助判定、悪化防止、代表入力、戻し方を含める。
   完了条件: A/B開始メモの全項目が埋まり、A案の証拠があり、合格ラインと戻し条件が明記されていること。1つでも欠けたら編集せず、開始不可または材料取得へ戻す。この完了条件を満たすまで、次のステップに進んではならない。

2. **プロ事例に沿って計画する**: 参照資料を読み、仮説、1つだけ変える点、主判定、補助判定、悪化防止、代表入力、戻し方を必ず書くこと。
   必須資料: [references/evidence-sources.md](references/evidence-sources.md) をこの工程に入ったら必ず読む。
   任意資料: 報告の完成形を迷う場合だけ [examples/good-output.md](examples/good-output.md) を読む。
   入力: A/B開始メモ、プロ事例の根拠、実例データ、評価に使う入力セット。
   出力: A/B計画。変更する1点、変えない範囲、代表ケース3件、既知失敗ケース1件、境界ケース1件、主判定1つ、補助判定1〜3つ、悪化防止2〜5つ、無効条件を含める。
   完了条件: 変更点が1つに絞られ、各判定に測り方と合格ラインがあり、入力セットが実運用に近いこと。入力が3件未満なら改善確定にしない。5件未満なら暫定採用条件を明記する。この完了条件を満たすまで、編集してはならない。

3. **変更前を実ルートで出す**: 実際の作成ルートを通し、変更前の成果物を必ず保存または報告できる状態にすること。
   入力: A/B計画、実入力、現行ルート、現行スキルまたは現行プロンプト。
   出力: A案の実出力、実行条件、使用した入力、保存場所または本文。
   完了条件: A案の本文または成果物、実行条件、確認結果、エラー有無が残っていること。スキル改善の場合は、対象エージェントが対象スキルの入口から自立実行し、必要工程と実例参照を読んだログがあること。A案が出ない場合、または検証者の手入力で工程を代替している場合はA/B無効として原因調査へ進み、B案作成に進んではならない。

4. **1点だけ変更してB案を出す**: A/B計画に書いた1点だけを変更し、同じ入力と同じルートでB案を必ず作ること。
   入力: A/B計画、対象ファイル、A案と同じ実入力、A案と同じ実行ルート。
   出力: B案の実出力、変更差分、実行条件、使用した入力、保存場所または本文。
   完了条件: 変更点が1つだけで、A案と同じ条件でB案が出ており、B案の本文または成果物と実行条件が残っていること。スキル改善の場合は、B案も対象エージェントが対象スキルの入口から自立実行していること。途中で検証者が差し戻し指示や文体指示を追加して別ルートにした場合、または別の改善を混ぜた場合は無効にする。この完了条件を満たすまで、判定に進んではならない。

5. **実物を横並びで判定する**: A案とB案の実出力を必ず目視比較し、良くなった点、悪くなった点、未確認点を分けること。
   必須資料: 判定前に [references/measurement-rubric.md](references/measurement-rubric.md) を必ず照合する。
   入力: A案、B案、勝ち負け基準、悪化防止基準。
   出力: A/B判定。主判定、補助判定、悪化防止、良くなった点、悪くなった点、未確認点、残す/戻す/無効の理由を含める。
   完了条件: 実物を横並びで見て、主判定が合格ラインを超え、悪化防止に違反していないことを確認していること。違反や材料不足があれば戻すまたは無効にする。この完了条件を満たすまで、完了報告してはならない。

6. **レビュー担当を使う場合は材料を揃える**: 別担当、読者役、サブエージェントに判定させる場合は、A案、B案、変更した1点、主判定、合格ライン、悪化防止、実入力、根拠データを渡すこと。
   入力: A/B計画、A案、B案、実入力、根拠データ、本人実例または良例。
   出力: レビュー依頼パック、レビュー結果、材料不足の有無。
   完了条件: レビュー担当が、残す/戻す/無効のどれかを、実物比較と基準に沿って出していること。レビュー担当には、要約ではなくA/B本文、本人実例3〜5件、チャンネル実例、改行と段落の比較、実行ログを渡すこと。材料不足なら本文修正へ進まず、A/B無効または前工程戻しにすること。レビュー担当の新しい案を採用する場合は、別A/Bとして最初から開始すること。

7. **残す/戻すを完了する**: 判定に従い、残す場合は検証してコミットし、悪化または無効なら必ず戻すこと。
   必須資料: 報告前に [references/report-template.md](references/report-template.md) を必ず読む。
   任意資料: 完成形の確認が必要な場合だけ [examples/good-output.md](examples/good-output.md) を読む。
   入力: A/B判定、差分、検証結果。
   出力: A/Bテスト報告、残した変更または戻した変更、検証結果、コミット。
   完了条件: 全ステップの実行、検証、最終状態、次の1テスト、コミットまたは戻し結果が明記されていること。残す場合は検証とコミットまで終える。この完了条件を満たすまで、完了報告してはならない。

## エッジケース

| 状況 | 対応 |
|:---|:---|
| 変更前の実出力がない | 先にA案を出す。出せない場合はA/B無効として編集しない |
| 複数箇所を直したい | 1回のA/Bでは1点だけに分割する。まとめて変えない |
| B案が悪化した | その変更は戻す。さらに直す場合は別のA/Bとして始める |
| レビュー指摘を手で足して文章を直した | 対象スキルの実行結果ではないため無効。新しいA/Bとして、スキル本体を1点だけ直してから同じ入口で再実行する |
| 実行エラーでB案が出ない | エラー原因を調べ、直せない場合はA/B未完了として報告する |
| ユーザーが生データを指定した | スキルが直接読む場所に全文生データを置く。抜粋や別参照で代替しない |
| 測定基準や合格ラインが曖昧 | A/B開始不可。先に `measurement-rubric.md` の形式で定義する |
| レビュー担当に渡す材料が不足 | レビュー無効。本文をこねず、材料取得またはA/B設計へ戻す |

## 禁止事項

- 変更前の実出力を見ずに編集してはならない。
- 測定基準と合格ラインなしに編集してはならない。
- 複数の原因を同時に変えて「改善した」と報告してはならない。
- チェックが通っただけで、文章品質が上がったと報告してはならない。
- 実際の本文を出さずに、点数や要約だけでA/B完了にしてはならない。
- 良くなった根拠がない変更を残してはならない。
- ユーザーが実例や生データを求めた時に、作り物の例で代用してはならない。
- レビュー担当の指摘を、A/B判定なしにそのまま本文修正へ流してはならない。
- 検証者が対象エージェントに工程ごとの修正指示を足し、対象スキルの自立実行結果のように扱ってはならない。
- 材料不足を、文章表現だけの推敲で解決したことにしてはならない。

## 自己完了確認

完了報告前に必ず確認すること。

- A/B計画に、測定基準、合格ライン、悪化防止、戻し条件がある。
- A案とB案を同じ入力、同じルート、1つだけの変更で出した。
- スキル改善では、対象エージェントが対象スキルを自立実行したログがある。
- 実本文または実成果物を横並びで見た。
- 残す、戻す、無効のどれかを根拠付きで決めた。
- レビュー担当を使った場合、必要な材料を渡した。渡せていなければ無効にした。
- 残す場合は検証とコミットまで終えた。
