# スキル品質チェックリスト

Skill Checker がスキルの品質を判定する際に使用するチェックリスト。
旧共有ルールの内容をチェック形式に変換したもの。

---

## カテゴリ1: 仕様準拠

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | YAML frontmatter | `name` と `description` が両方あるか |
| 2 | name形式 | 表示名が読みやすく、ディレクトリ名が小文字英数字+ハイフンか |
| 3 | description長と内容 | 200文字以内で「何をするか」「いつ使うか」を含むか。三人称か |
| 4 | SKILL.md本体のトークン数 | 2,000トークン以下か（文字数÷4で概算） |
| 5 | 時間依存情報 | 日付・バージョン番号をSKILL.md本体に含んでいないか |

---

## カテゴリ2: 内容品質

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | 概要 | 1-2文でスキルの目的を説明しているか |
| 2 | ワークフロー形式 | チェックリスト形式か。各ステップに操作手順・入出力・完了条件があるか |
| 3 | 具体例 | 最低2つあるか。抽象例でなく実際の入力→出力の対か。examples/に分離されているか。文章・投稿・文体・マーケティング系では、作成者が想像した完成文を実例として置いていないか。`プロ事例` は検索、公式資料、ユーザー提供例、ローカル実ファイルのいずれかで実物確認済みで、参照元名、出典パスまたはURL、実本文または実際のプロンプト本文を含むか |
| 4 | エッジケース | テーブル形式で3件以上あるか |
| 5 | 禁止事項 | 明記されているか |
| 6 | 冗長性排除 | AIが既知の情報や不要な説明を書いていないか |
| 7 | 選択肢制限 | 推奨方法1つか。代替は必要な場合のみか |
| 8 | 用語一貫性 | 同一概念に複数の呼び方を使っていないか |
| 9 | 義務表現 | 必須指示に「必ず」等の義務表現があるか |
| 10 | ツール使用明示 | ツール使用前提の場合、自動実行を明記しているか |
| 11 | Cron互換性 | payload.messageにスキル内部手順をハードコードしていないか |
| 12 | 材料確認 | ユーザー提供例、生データ、公式資料、公開されているプロ事例、ローカル実ファイル、未確認材料を分けているか |
| 13 | 会話混入防止 | ユーザーが作業者へ向けた今回だけの注意、感情的な表現、進行中の叱責、A/Bテスト、検証者の作業メモをそのままスキル本文に入れていないか |
| 14 | 見出し品質 | 短すぎて意味が伝わらない見出しや、担当者しか分からないラベルを使っていないか。不自然な見出し禁止語が残っていないか |
| 15 | プロンプト成果物のMarkdown品質 | プロンプト、テンプレート、文章作成手順を成果物にする場合、標準で山括弧タグ、JSON、YAMLだけの形式にせず、Markdownの見出し、箇条書き、表で自然に読める形になっているか。プロ事例のタグ構造を引き継いでいないか。三点リーダー、未定稿表記、穴埋め指示のような未完成の文が残っていないか |
| 16 | プロンプト実行可能性 | プロンプト成果物に、何をするか、使う材料、見る観点、作業手順、出力形式、確認方法、不合格時の対応が読み取れるか |

## カテゴリ3: プロジェクトルール準拠

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | 日本語テキスト | 全テキストが日本語か |
| 2 | 素人向け表現 | 非エンジニアにも理解できる表現か |
| 3 | パスのハードコード禁止 | ファイルパスが動的解決されているか |
| 4 | フォルダ名非依存 | ディレクトリ名変更で壊れないか |
| 5 | scripts品質 | scripts/がある場合、pro-quality-standards.md準拠か |

---

## カテゴリ4: description品質

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | 必須要素 | 目的・自動発火条件（義務表現付き）・トリガー語・成果物が全てあるか |
| 2 | 具体性 | 具体的なキーワードを含むか（「ファイルを処理する」はNG） |
| 3 | トリガー語 | ユーザーが使いそうなフレーズを含むか |
| 4 | 曖昧性排除 | 曖昧な表現だけでないか |

---

## カテゴリ5: テストと評価

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | 仕様準拠チェック | カテゴリ1の自動チェックが実行されたか |
| 2 | 内容品質チェック | カテゴリ2の自動チェックが実行されたか |
| 3 | 実動作テスト | 最低1シナリオの実動作テストが実行されたか |
| 4 | 異常系テスト | エッジケースの状況を実際に試したか |
| 5 | 修正ループ | 不合格→修正→再チェック（最大3回）が実施されたか |

---

## カテゴリ6: 構造とファイル配置

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | 公式推奨構造 | SKILL.md（入口・手順・エッジケース・禁止事項・自己完了確認）+ references/（詳細）+ examples/（具体例）の構造か |
| 2 | ネスト制限 | ファイルパスが1階層以内か |
| 3 | 依存宣言 | 依存パッケージがfrontmatterのdependenciesに記載されているか |
| 4 | 本体内容 | SKILL.mdが必要資料を各工程内に含めた手順アウトライン、エッジケース、禁止事項、自己完了確認に絞られているか |
| 5 | 具体例の分離 | 入力→出力ペアがexamples/にあるか |
| 6 | 参照ナビゲーション | references/やexamples/を、該当工程の中で必要になった時だけ読む形で明示しているか |
| 7 | 分離省略条件 | 80行以下で、判断ルール・表記ルール・品質基準・ツール仕様・プロ事例・生データがない場合のみreferences/省略可か |
| 8 | 複雑作業の分離 | 複雑な工程がある場合、references/内の1階層番号付きファイルへ分けているか。prompt-index.mdやprompt-quality-requirements.mdを標準生成していないか |
| 9 | referencesの実作業粒度 | 判断ルール、表記ルール、品質基準、複雑工程、プロンプト生成、生データ、プロ事例のために references/ を作る場合、各ファイルに目的、使う材料、見る観点、作業手順、出力形式、確認方法、不合格時の対応のうち必要な項目があり、3〜5個の浅い手順だけで終わっていないか |

---

## カテゴリ7: スキップ防止パターン

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| 1 | 義務表現 | 必須ステップ（検証/品質チェック/最終報告）に義務表現があるか |
| 2 | ゲート条件 | 各ステップに「〜を満たすまで次に進んではならない」があるか |
| 3 | 自己完了確認 | 最終ステップに全ステップ振り返りチェックリストがあるか |

---

## 構造品質チェック（S1-S16）

| # | チェック項目 | 判定基準 |
|:--|:-----------|:--------|
| S1 | トークン数 | SKILL.md本体が2,000トークン以下か |
| S2 | 情報密度 | ドメイン固有ルール・判定テーブルがSKILL.md内に混在していないか |
| S3 | 具体例の分離 | 入力→出力ペアがexamples/に分離されているか |
| S4 | 参照ナビゲーション | references/やexamples/を該当工程の中で必要時に読む明示があるか |
| S5 | 具体例の品質 | 抽象的でなく実際の入力→出力テキストか。文章・投稿・文体・マーケティング系では作り物の完成文を実例にしていないか。`プロ事例` は実物確認済みで、参照元名、出典パスまたはURL、実本文または実際のプロンプト本文を含むか |
| S6 | 本体の簡潔さ | 必要資料を各工程内に含めた手順アウトライン、エッジケース、禁止事項、自己完了確認に絞られているか |
| S7 | 会話混入防止 | ユーザーが作業者へ向けた今回だけの注意が、スキル本文にそのまま入っていないか |
| S8 | references省略判定 | 判断ルール・表記ルール・品質基準があるのにreferences/を省略していないか |
| S9 | 作り物の具体例防止 | 作成者が想像した完成文や、出典と本文がない抽象メモを、実例・良い例・プロ事例として置いていないか |
| S10 | 見出しの分かりやすさ | 短すぎて意味が伝わらない見出しや作業者だけが分かるラベルがないか |
| S11 | プロンプト成果物のMarkdown品質 | プロンプト、テンプレート、文章作成手順が成果物の場合、山括弧タグではなく自然なMarkdown文書として読めるか。プロ事例のタグ構造を引き継いでいないか。三点リーダー、未定稿表記、穴埋め指示のような未完成の文が残っていないか |
| S12 | 材料確認 | ユーザー提供例、生データ、公式資料、公開されているプロ事例、ローカル実ファイル、未確認材料を分けているか |
| S13 | 検証作業の混入防止 | A/Bテスト、検証者の作業メモ、今回だけの注意をスキル本文へ混ぜていないか |
| S14 | プロンプト実行可能性 | プロンプト成果物に、何をするか、使う材料、見る観点、作業手順、出力形式、確認方法、不合格時の対応が読み取れるか |
| S15 | 不自然な日本語見出し | `戻り方`、`出すもの`、`止める条件`、`戻る場所`、`自然な日本語で固定`、単独の `本文`、単独の `指示文` が見出しやラベルに残っていないか |
| S16 | 成功法則の根拠 | 成功法則、成功パターン、改善前後、A/B結果、レビュー結果を使う場合に、根拠となる実物、採用理由、使える条件、使ってはいけない条件が分かれているか |

※ SKILL.md 80行以下で、判断ルール・表記ルール・品質基準・ツール仕様・プロ事例・生データがない場合、S2-S4はn/a可
